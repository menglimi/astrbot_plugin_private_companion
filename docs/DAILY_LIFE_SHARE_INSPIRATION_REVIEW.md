# daily_life 与 daily_share 借鉴评审

> 导航：[设计总纲](./FRAMEWORK_DESIGN.md) / [主题目录](./FRAMEWORK_DESIGN_INDEX.md)。定位：外部调研依据；吸收结论由角色与主动设计维护。

这份评审基于两个仓库的实际代码结构与文档：

- `astrbot_plugin_daily_life`：生活状态、记忆、关系、主动行为、现实感知与多模态生活背景。
- `astrbot_plugin_daily_share`：内容生成、调度、投递、目标管理、跨插件桥接与失败恢复。

目标不是把两个插件搬进新框架，而是提取可以服务于新陪伴体系的设计能力，并把其中仍然依赖固定类型、固定时间或固定话术的部分重新交给 AI 做语义决策。

## 1. 最值得吸收的部分

### 1.1 daily_life：把“拟人感”建立在连续状态上

| 设计 | 可吸收方式 | 对应主线 |
| --- | --- | --- |
| 三层情绪与半衰期（`core/life/affect.py`） | 短时情绪、日内心境、关系感受分开保存；每次变化必须带证据，随时间衰减 | 记忆、主动 |
| 时间化事实（`core/archive/knowledge.py`） | 用 `subject/predicate/object/valid_from/valid_to/provenance` 表示事实，更新时保留被替代版本 | 记忆、现实触及 |
| 记忆边界与作用域（`core/models/boundaries.py`、`core/archive/experience/lexicon.py`） | 记忆跨私聊、群聊、公开空间前先经过 scope policy；不再靠词表阻断 | 记忆、现实触及 |
| 观察—裁定—回执链（`core/archive/perception.py`、`core/archive/knowledge.py`） | 把“看见了”“决定不回应”“执行成功”分别存为 Observation、Decision、Receipt | 主动、实时共处 |
| 关系与行为经验（`acquaintances.py`、`experience/patterns.py`、`experience/reactions.py`） | 保存场景、证据、支持次数、置信度和结果；AI 负责从多轮互动归纳模式 | 记忆、主动 |
| 会话中途摘要与聊天记忆队列（`experience/patterns.py`、`archive/queue.py`） | 长会话分段压缩，使用可恢复批次、游标、退避和死信，避免每轮强行写长期记忆 | 记忆、实时共处 |
| 可恢复任务（`archive/knowledge.py`） | 每个后台任务有幂等键、租约、重试次数、完成/失败/取消/过期状态 | 三条主线共同基础 |
| 活动、地点、路线、饮食、家务统一时间线（`archive/activity.py`） | 现实触及不只记录传感器值，也记录活动上下文和行动结果 | 现实触及 |
| 视觉/视频洞察缓存（`core/sight/*`） | 将媒体输入转为带时间、来源、指纹和 TTL 的 Insight；过期后重新观察 | 现实触及、实时共处 |
| 反馈学习（`experience/reactions.py`） | 只有用户后续行为或明确反馈才改变表达偏好；没有反馈不猜测态度 | 记忆、主动 |
| 提示词中的证据清单（`core/life/rhythm.py`） | 先列可引用证据，再让 AI 输出记忆、偏好、事件、决策结果、情绪和关系变化；禁止从活动文案词语或标点猜结论 | 记忆、主动 |
| Provider 熔断与退避（`core/life/reliability.py`） | 连续失败后短暂熔断并冷却，区分可重试与不可重试错误 | 全部插件 |

其中最重要的不是“有很多字段”，而是每个字段都能回答：**什么时候观察到、谁提供的、可信度如何、现在是否仍有效、之后是否被真实结果修正。**

### 1.2 daily_share：把“主动”建立在任务与投递闭环上

| 设计 | 可吸收方式 | 对应主线 |
| --- | --- | --- |
| `TaskRuntime` 显式依赖容器（`core/tasks/runtime.py`） | 每个能力只拿到声明过的服务，不跨模块调用私有方法 | 全部插件 |
| 生命周期服务（`core/host/lifecycle.py`） | 运行态、后台任务集合、资源排空、停止与重载有统一状态机 | 实时共处、现实触及 |
| 统一模型调用与有限回退（`core/host/model.py`） | 总超时预算覆盖重试；区分永久错误与暂时错误；终止时立即停止 | 全部插件 |
| 目标权限按完整 UMO 匹配（`core/host/permission.py`） | 目标、平台、机器人实例、会话类型绑定在结构化 TargetRef 中 | 现实触及、主动 |
| 发送历史和降级记录（`core/database/history.py`） | 每次投递记录 success、failure、media、degraded、reason；成功后才写活动和记忆 | 主动、记忆 |
| 新闻只追加快照（`core/database/newssnapshot.py`） | 用户追问读取当时成功发送的证据快照，不重复抓取或改写过去 | 记忆、创作 |
| 域状态表（`core/database/state.py`） | 状态按 domain/key/version 读写，避免把所有运行状态塞入自然语言 | 全部插件 |
| 调度恢复（`core/tasks/scheduler/recovery.py`） | 重启后只恢复未来或近期错过的任务，过期任务进入终态 | 主动、实时共处 |
| 失败可降级投递 | 图片/语音失败时保留文字；能力缺失返回结构化 unavailable，不伪造成功 | 生图、直播、现实触及 |
| 与 daily_life 的窄桥接（`core/integrations/dailylife.py`） | 跨插件只暴露公开 DTO，不共享数据库、不读取私有实现 | 插件体系 |

跨插件上下文还应沿用 daily_life 的精确目标隔离：私聊只导出该联系人相关记忆，群聊只导出当前群作用域，公开目标只导出无人物关联的公共片段；原始回复、证据编号、数据库 ID 和治理字段不跨边界暴露。可统一成带 `target_scope`、`visibility`、`redaction` 的 `ContextContribution`。

这里值得借鉴的是“主动行为的工程闭环”，而不是它的“问候/新闻/心情”等固定内容类别。

两个仓库的测试也很有参考价值：daily_life 用场景测试验证记忆批次、主动回访、动作回执、媒体恢复和作用域隔离；daily_share 的架构测试验证事件发送集中、服务不调用私有方法、桥接单例和降级状态。新框架应把这些测试改造成跨插件 contract/eval corpus，特别覆盖旧硬编码审计表中的反例。

daily_life 已经把“不要靠固定词触发”“不按固定场景或随机概率主动分享”“时间轴按真实生活自然增减”等负向要求写进提示和回归测试。新体系应保留这种测试思想：用同义表达、否定、引用、反话、无关键词和多意图输入验证语义裁定，而不是继续维护一张更大的词表。

## 2. 必须重做的部分

### 2.1 不直接继承固定枚举和固定话术

daily_share 的 `ShareType`、`新闻/心情/知识/推荐` 序列、Cron 与固定间隔适合内容分发产品，但不应成为陪伴核心的行为入口。新框架应让 AI 先产生 `IntentGraph` 与 `MotivePlan`，再由能力提供者判断能否执行。类型只能作为可选标签，不能限制 AI 只能在几个栏目中选择。

同理，daily_life 中的固定动作集合、固定状态字段和固定 JSON 提示可以作为协议兼容层，但角色的实际体验应允许 AI 组合出未预先枚举的行为；代码只校验权限、资源、时间、幂等性和安全前置条件。

### 2.2 不把“主动”简化成定时器

`daily_share` 的智能定时、随机时段和最小间隔可以吸收为调度能力，但“现在要不要靠近谁、以什么方式靠近、是否值得打扰”必须由 AI 根据关系、未完话题、情绪、现实状态和近期互动共同裁定。调度器只负责唤醒候选、持久化等待、取消过期计划和执行预算。

### 2.3 不把自然语言协议当作内部 API

类似“已发送”“已挂起”“已完成”的文本只能作为用户可见表达。插件之间必须传递 `ActionRequest`、`OperationResult`、`DeliveryReceipt`、`EvidenceRef` 等结构化对象，避免模型输出一句话就改变系统状态。

### 2.4 不复制旧的词汇过滤思路

两个仓库中仍可见的类型解析、参数别名、平台判断和文本清洗，只能保留在边界适配层。情绪、关系、意图、是否在开玩笑、是否引用他人话、是否真的答应等问题，统一交给 AI 语义层，并将不确定性与证据写入结果；不能再增加“更多关键词”来修补误判。

## 3. 映射到新陪伴体系

### 第一优先级：记忆、现实触及、实时共处

1. **记忆底座**：吸收时间化事实、来源优先级、记忆边界、关系作用域、会话中途摘要、可纠正版本、反馈效果和可恢复写入队列。
2. **现实触及**：吸收 Observation/Decision/Receipt 三段式、活动与地点上下文、媒体洞察 TTL、权限与凭据隔离、能力不可用时的透明降级。
3. **实时共处**：吸收 Runtime 生命周期、SessionRecord、取消与排空、实时转写分轮、临时上下文、跨重启恢复和统一总预算。

### 第二优先级：生图、创作、直播、屏幕、游戏

- 生图：采用 daily_life 的媒体洞察与素材指纹、daily_share 的成功投递后记忆回写；由 AI 决定是否值得生成及是否分享。
- 创作：采用版本化内容、证据快照和异步任务；QQ 空间工作台暂不进入当前主线。
- 直播：采用实时会话、事件流、字幕/音频回执和生命周期排空。
- 屏幕：沿用现实观察的权限、时间窗、来源和过期语义，默认只保存摘要而非原始画面。
- 游戏：采用房间/玩家/回合事件和可恢复任务；游戏规则由具体游戏能力提供，不写入陪伴核心。

`astrbot_plugin_bug_companion` 与 Content 中的 QQ 空间部分继续作为后续治理/工作台方向，不阻塞前三项建设。

## 4. 建议形成的统一对象

```text
Observation       AI/设备/平台看到的事实，带 source、scope、observed_at、confidence
IntentGraph       AI 对用户意图、隐含目标、多意图与不确定性的解释
AffectEvent       有证据的短时/日内/关系变化
MotivePlan        是否靠近、等待、观察、分享或执行，以及原因和代价
ActionRequest     需要某能力执行的结构化请求，含权限、幂等键、预算
OperationResult   能力执行结果，区分成功、部分成功、暂不可用、永久失败
DeliveryReceipt   平台实际投递回执
MemoryProposal    AI 建议沉淀、修正、降权或删除的记忆
EvidenceRef       可追溯来源，控制跨作用域暴露范围
```

推荐的主动链路是：

```text
唤醒候选 → 读取作用域快照 → AI 形成 Intent/Motive → 前置条件与权限校验
→ 创建 ActionRequest → 执行/重试/降级 → DeliveryReceipt
→ 仅依据真实结果写入 MemoryProposal 与 AffectEvent
```

## 5. 结论

这两个插件最有价值的借鉴点是：daily_life 提供了“连续的内在生活模型”，daily_share 提供了“可恢复的外部行动模型”。新陪伴框架应把二者合并成“AI 决定意义，结构化运行时保证事实”的体系：AI 可以自由理解、组合和改变行为，代码只守住权限、证据、作用域、协议、预算、幂等和生命周期这些不可交给自然语言的边界。
