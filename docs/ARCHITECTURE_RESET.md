> **文档状态**：架构讨论基线，2026-09-06 完成一致性审查。除 3.16 标明的现有兼容切片外，其余均为目标设计，不代表已实现或通过运行验收。本次修订与待验证事项见 [DESIGN_REVIEW_20260906.md](./DESIGN_REVIEW_20260906.md)。
>
> **文档定位**：第 1--2 节说明范围和问题；第 3 节说明目标架构与领域决策，3.14 汇总现有插件差距和补齐主线，3.15 给出可立即执行的改造审计入口；第 4--5 节说明迁移顺序和首批切片；第 6 节是所有阶段都不能破坏的不变原则。
>
> **当前主线结论**：陪伴核心与原生联动插件从构建初期共同设计和验证，首期范围见 3.1.1 与 5.2；Kernel 先留在陪伴核心内部；插件通过版本化 DTO 和能力协议协作；日历是事实源、日计划是投影，活动经历通过 `PersonaContinuityState` 沉淀为角色连续生活；主动行为采用统一机会调度，并由对话占用态保护当前连续互动；情绪通过事件、状态、动机和表达姿态调制角色，不直接发送消息。
>
> **阅读顺序**：先看第 2 节确认重置动因，再看 3.1--3.6 的边界和基础设施，随后按 3.7（日历）、3.10（情绪/动机）、3.12（主动）阅读领域方案，再看 3.14 的差距主线和 3.15 的现有插件审计清单，最后看第 4--6 节的执行约束。

### 文档使用与决策状态

当前稿对陪伴核心的设计更详细，这是需要在构建初期补齐的设计缺口。原生联动插件从阶段 0 共同确定用例、数据所有者、失败流程、接入契约和验收案例；公共契约经原生联动验证后再定型。各插件完整业务改造和数据迁移可以分批实施，首期联合设计与验证不能因此后移。

- 本稿负责架构边界、领域语义和实施依赖；[注入协议](./COMPANION_INJECTION_PROTOCOL.md) 负责对外字段和版本；[审计清单](./EXISTING_PLUGIN_AUDIT.md) 记录带日期的代码证据。
- `Scope` 是兼容载体，`RuntimeScope` 是调用上下文；稳定的数据归属另见 3.2.2。`LLM Gateway`、`ModelGateway` 统一指模型调用边界；`DeliveryManager` 是 `DeliveryGateway` 内部的投递状态管理职责，不各建一套运行时。
- `CalendarProjection` 负责构建 `ScheduleProjection` 与 `TemporalDecisionContext`；`TemporalRecord` 是时间记录契约，`CalendarCommitment` 是其中的承诺语义，不作为相互复制的事实库。
- 本文中的 Projector、Arbiter、Registry 等名称首先表示职责，可由现有模块内的函数或接口实现；只有独立生命周期、数据所有权或实际复用需要时才拆成新模块。
- 设计要求通过对应切片的契约和行为验证后才成为稳定约定。修改语义时同步更新协议及受影响案例，不能用设计文字覆盖现有 SDK 的版本行为。

## 2. 现状问题

### 2.1 宿主边界不清

- 多个插件通过 `sys.modules`、`get_registered_star`、模块级单例和私有属性互相发现。
- 扩展 API 虽然已经有版本和状态检查，但能力仍常以宿主私有方法名传递，调用方需要知道实现对象结构。
- 记忆、创作、图片、现实、直播等桥接均有各自的重试、热加载和兼容路径，生命周期语义不一致。

### 2.2 状态和持久化分散

- 陪伴核心同时维护 JSON、SQLite、迁移标记、人格数据库和镜像文件。
- 每个插件又有自己的 JSON/SQLite/缓存/临时目录，跨插件状态通过复制或回写同步。
- 保存、压缩、迁移和热重载没有统一的事务与取消语义；一个插件的后台任务可以在宿主已失效时继续持有对象。

### 2.3 日程仍然是多套模型

- `daily_plan`、`schedule_adjustments`、`calendar_events`、`calendar_rules`、`calendar_exceptions` 和观察活动并存。
- 日历契约和 reconciler 已经在演进，但每日计划仍承担事实、意图、执行和提示词上下文多种含义。
- 时间解析、跨日、时区、重复规则和例外在不同模块有重复逻辑，导致“日期耦合不足”和日程死板同时存在。

### 2.4 平台和传输层泄漏到业务

- 业务代码直接判断 `aiocqhttp`、QQ 官方、OneBot、WebSocket、桌面设备等平台细节。
- 同一类“发送消息、取图片、获取会话、绑定用户”的能力在多个插件重复实现，兼容矩阵随功能增长。
- 元数据声明的支持平台与实际能力探测、页面入口和降级策略没有统一来源。

### 2.5 页面层和后台任务放大资源开销

- 核心页面 API 是超大单体，多个扩展各自拥有页面 API、静态资源甚至独立 Quart/Hypercorn 服务。
- 初始化期间会创建多组长期任务；屏幕、直播、现实、游戏和共处各自维护循环、缓存和连接池。
- 缓存上限、采样、刷新频率和网络退避由功能自行决定，无法按全局资源预算协调。

### 2.6 聚合依赖图被实现细节绑住

当前系统的依赖关系不是“安装一个主插件、其它插件只是菜单项”，而是一个运行时互联图：

| 插件 | 对陪伴核心的关系 | 其它运行时边界 | 独立资源/服务特征 |
| --- | --- | --- | --- |
| `private_companion` | 聚合宿主，提供人格、作用域、主链、主动行为和面板 | 被多个扩展反向探测 | 约 2.1 万行主逻辑、约 3.1 万行页面 API、数百个任务/兼容入口 |
| `memory_companion` | 可选核心桥；缺失时陪伴降级长期记忆 | 反向读取陪伴页面/状态并维护桥接 | 独立记忆存储、召回评测、页面兼容层 |
| `content_companion` | 依赖陪伴核心管理作品和旧数据 | 可选调用 `image_companion`、记忆桥 | 创作状态 JSON、封面文件、少量后台任务 |
| `image_companion` | 可独立提供生图，但由陪伴核心发现和授权 | 对模型/图片后端做能力探测 | 生图状态、参考图目录、调试事件和图片任务 |
| `reality_companion` | 依赖陪伴核心进行身份、主动行为和状态回写 | 米家、移动网关、摄像头、音频等设备适配 | 多个设备/网络任务，独立 JSON 状态和认证文件 |
| `screen_companion` | 通过 API 接入陪伴主链和共享活动 | 屏幕采集、远程接收、可选输入/麦克风 | 多个采集/处理任务、Web 服务、日记和学习 JSON |
| `together_companion` | 依赖陪伴核心人格/记忆/消息投递 | 发现屏幕、直播、记忆桥 | 通话/房间 Web 服务、媒体解析、令牌和会话任务 |
| `game_companion` | 依赖陪伴核心上下文和邀请能力 | 自有游戏房间和浏览器客户端 | 独立 Web 服务、房间生命周期、引擎资源 |
| `live_stream_companion` | 依赖陪伴核心上下文、主动能力和记忆写回 | B 站/Twitch、OBS、VTS、TTS | 长连接/轮询任务、直播页面、字幕和外设连接 |
| `bug_companion` | 业务上可独立运行；可读取聚合诊断/群作用域 | GitHub、群历史、人工审批 | 独立 SQLite、归档 JSONL、恢复/重试/仓库播报任务 |

代码层面，这张图主要通过 `sys.modules`、`get_registered_star`、模块级活动实例和事件私有属性实现。它导致插件加载顺序、热重载、缺失扩展和版本不兼容时出现多套“发现/重试/降级”语义。重置时必须把这些边变成显式的能力注册和版本化 DTO；插件之间不能再以对象私有字段作为协议。

### 2.7 服务与数据所有权清单

重置前应把“插件页面”和“插件服务”分开统计。当前至少存在以下服务边界：

| 边界 | 当前实现 | 重置目标 |
| --- | --- | --- |
| AstrBot Dashboard API | 核心、记忆、屏幕、直播、问题治理等分别调用 `register_web_api` | 由 Workspace Gateway 统一鉴权、错误格式和分页；扩展只注册资源处理器 |
| 陪伴独立 WebUI | `private_companion/standalone_webui.py`，依赖 Quart/Hypercorn | 保留为可选管理入口，复用 Gateway，不复制业务路由 |
| 屏幕服务 | `screen_companion/web_server.py`、远程 WebSocket 接收 | 采集任务由 Supervisor 管理，服务只提供受限媒体流和状态查询 |
| 共处房间 | `together_companion/server.py` | 房间生命周期、票据和媒体会话纳入统一 Session/Delivery 接口 |
| 游戏房间 | `game_companion/server.py` | 游戏引擎保持 Feature 内部，房间鉴权和销毁由统一 Session 管理 |
| 现实移动网关 | `reality_companion/mobile_gateway.py` | 作为显式 Device Adapter；令牌、位置和设备数据通过能力权限进入 Kernel |
| 直播字幕/外设 | `live_stream_companion/subtitle_server.py` 及 B 站/Twitch/VTS/OBS 连接 | 长连接注册为 Supervisor 任务，字幕和外设动作使用 Delivery/Device DTO |

数据所有权也必须显式化：`private_companion` 的领域服务负责人格、关系、日历事实和主动队列；`memory_companion` 负责长期记忆记录、索引及其写入/修订/删除策略；各 Feature 只写自己的业务命名空间；`bug_companion` 的问题库仍可独立存在。Kernel 保存调用所需的引用和有期限的投影。跨域结果通过事件或公开用例传递，不直接访问另一个插件的 `data_dir` 同步；迁移工具的受控读取另按迁移清单登记。

### 2.8 提示词、策略和事实边界混在领域代码

- 日程、创作、观影、直播、关系和记忆均在业务函数中拼接长提示词。
- 证据等级、用户输入、外部资料、内部状态和执行回执的约束虽有局部实现，但没有统一的上下文类型和审计结果。
- 失败时容易通过兼容回退继续执行，却缺少统一的能力降级报告。

## 3. 目标架构

### 3.1 分层

```text
AstrBot 事件/Provider/存储接口
                 |
          Companion Kernel
  scope  time  event  policy  llm  delivery  lifecycle  capability
                 |
       Feature Services (可选、无私有字段依赖)
 memory content image reality screen together game live bug
                 |
       Platform / Provider / Device Adapters
```

1. **Kernel** 是陪伴体系内的协调运行时，提供作用域解析、时钟、事件、能力协商、调用与投递边界及任务监督。日历、关系、情绪和主动评分属于陪伴核心内的领域服务，Kernel 不拥有其算法。AstrBot 继续负责原生事件、Agent、Provider 和插件生命周期。
2. **Feature Service** 只拥有自己的领域状态和用例，通过版本化 DTO 与 Kernel 通信；未安装时能力不存在，不启动替代循环。
3. **Adapter** 把平台、模型、图片、设备和网络协议转换成统一接口。领域代码不得出现平台类型判断。
4. **Admin/diagnostic** 是横切能力，问题治理可以读取审计事件和知识索引，但不应读取陪伴核心私有状态。

首期不新增强制安装依赖。先把 Kernel 提取为陪伴核心内的 `companion_kernel` 包，并以稳定的 `companion_sdk` DTO/API 对外发布；等契约稳定后再决定是否拆成独立发行包。

外部注入协议的控制面/数据面边界、能力类型和 DTO 见 [COMPANION_INJECTION_PROTOCOL.md](./COMPANION_INJECTION_PROTOCOL.md)。主陪伴只管理扩展元数据、生命周期、能力状态和审计摘要；扩展继续持有领域实现、凭证、缓存和业务数据库。

### 3.1.1 原生联动插件的首期地位

原生联动插件指本体系已维护的记忆、创作、生图、现实、屏幕、一起、游戏、直播和问题治理插件。它们与陪伴核心共同构成首期设计对象：每个公共接口都要有真实生产方、消费方和失败场景，领域之间可以通过已协商的能力直接协作，Kernel 提供身份、授权、发现和协调，不中转全部业务数据。

“原生”表示共同维护和联动验证责任，不代表必须全部安装或拥有额外权限。部署仍支持按需安装，缺少插件只降级相关能力；原生与第三方使用相同的公开协议、版本协商和权限边界。下表列出的最小边界在阶段 0 设计、阶段 1 通过现有插件适配器验证，不等到完整领域迁移才处理。

| 原生插件 | 初期必须共同确定的边界 | 最小接入及缺失行为 |
| --- | --- | --- |
| `remember_you` | 记忆归属、断言及有效时间、答案证据预算、修订/撤回回执；与关系、日历、情绪余波的权威边界 | 当前/历史细节问答、纠正和证据保留验证，检查最终注入片段而非仅记忆 ID；缺失时明确长期记忆不可用，不新建替代记忆库 |
| `content_companion` | 作品 ID/版本、创作上下文、章节完成事件、封面请求及发布授权 | 核心请求作品上下文，创作按授权调用生图并引用结果；生图缺失时作品仍可保存 |
| `image_companion` | 参考图归属、异步任务、资源引用、生成与发送状态分离 | 同一生图请求供核心/创作调用；失败不伪造图片、不重发已成功文本 |
| `reality_companion` | 设备/用户绑定、观测新鲜度、提醒与日历关系、动作授权及回执 | 一次观测进入时间上下文/候选，一次受控动作返回回执；设备离线保留 unknown |
| `screen_companion` | 采集授权、活动主体、原始媒体保留、语义摘要和采样预算 | 活动摘要供陪伴与一起场景消费；断流后旧画面不能继续作为当前事实 |
| `together_companion` | 房间参与者、人格快照、共读/观影进度、临时上下文、离开后的记忆归属 | 一次加入、上下文贡献、离开和摘要回写；缺少记忆/屏幕插件仍可运行已具备的房间能力 |
| `game_companion` | 席位身份、对局事件、邀请、引擎生命周期和结束摘要 | 对局事件经核心形成表达/候选，结束时回收资源；引擎失败不伪造比赛结果 |
| `live_stream_companion` | 直播 Session、弹幕上下文、TTS/字幕/嘴型同步、聊天投递与实时输出的界限 | 一次直播事件进入人格表达并返回输出回执；重连不重放已完成演出，单项外设失败局部降级 |
| `bug_companion` | 跨插件诊断引用、问题来源、审批边界与隐私裁剪 | 读取一条原生联动失败的结构化诊断；无授权不读取私聊原文，缺失时核心诊断仍可用 |

每个插件补充一份最小契约记录，包含插件/能力版本、输入输出样例、owner_key、权限、生产方/消费方、超时/取消/卸载、缺失依赖、配置与工作区入口、对应验证编号。可放在该插件已有 docs 中，不强制新增统一框架或类层级。

核心初期需要同时考虑以下联动信息：一次调用的追踪标识及父请求、稳定的作品/媒体/房间/设备引用、人格绑定版本、来源证据、执行回执、取消传播和领域配置版本。引用只授予声明范围内的访问，不能因来自原生插件而扩大权限。长期记忆、情绪、日历与表达之间通过投影和事件相互影响，各自仍保留明确的写入所有者。

首期验证采用现有原生插件的真实适配入口。云模型、硬件、直播平台等外部边界可使用录制数据或测试替身，报告要注明覆盖范围；不能用仅能注册 manifest 的空插件代替领域契约验证。每个原生插件至少完成一项最小成功路径及适用的缺失、版本不兼容、重载失败验证，再由 5.2 的跨插件场景检验公共契约。没有真机或真实平台验证的能力仍标记待验证，不影响其他已验证能力按批发布。

### 3.2 核心契约

外部插件注入能力的字段、生命周期和 DTO 以 [COMPANION_INJECTION_PROTOCOL.md](./COMPANION_INJECTION_PROTOCOL.md) 为准；本节只保留架构层摘要。

跨插件业务数据使用不可变、可序列化 DTO；以下是基础类型摘要，领域协议可以按版本扩展。插件内部函数不强制序列化，宿主桥接层对 event/request 的使用见注入协议 6.3：

- `Scope`：平台、账号、会话、用户、群组和人格的完整作用域。
- `CapabilityDescriptor`：能力名、版本、生命周期、权限、资源预算和降级原因。
- `CompanionEvent`：输入、观察、计划、执行、结果和错误事件，带来源与证据等级。
- `TemporalRecord`：带 IANA 时区的绝对时间区间、重复规则、例外和来源引用。
- `ActionRequest` / `ActionResult`：发送、设备、媒体、页面和模型动作，包含幂等键与审计信息。
- `PromptRequest` / `PromptResult`：任务类型、结构化上下文、预算、提供商路由和校验结果。

兼容层只能把旧对象转换成这些 DTO，不能暴露或继续扩大旧私有字段。

### 3.2.1 多 Bot、多会话与多人格作用域

多 Bot 部署和多人格绑定不是高级功能，而是所有状态和插件接口的默认前提。Kernel 在收到 AstrBot 事件的第一步就必须解析出完整的 `RuntimeScope`；后续事件、记忆、日历、情绪、主动候选、任务和动作都不得重新猜测作用域。

`RuntimeScope` 至少包含：

```text
installation_id       AstrBot 部署或数据目录实例
bot_id                部署中的逻辑 Bot/代理身份
platform              当前平台类型
account_id            平台登录账号或连接身份
conversation_id       当前平台会话/群聊
session_id            当前线程、房间或临时交互会话
group_id / user_id    群和用户主体（可为空，但对象必须存在）
persona_id            本轮解析出的角色身份
persona_binding_revision 人格绑定版本
```

字段之间不能互相替代：`bot_id` 区分同一部署中的不同 Bot，`account_id` 区分平台登录身份，`persona_id` 区分角色设定，`conversation_id` 区分聊天空间，`session_id` 区分其中的临时线程。简单部署可以让部分值相同，但协议仍保留字段，避免以后扩展时改变主键语义。

人格绑定使用显式的 `PersonaBinding` 记录：

| 字段 | 作用 |
| --- | --- |
| `selector` | 绑定适用的 bot、会话、群、用户或 session 范围 |
| `persona_id` | 目标角色身份，不携带完整人格内容 |
| `precedence` | 解决多个匹配项的确定优先级 |
| `effective_from` / `effective_until` | 支持临时角色和定时切换 |
| `revision` | 绑定变更版本，写入每个下游 DTO |
| `source` / `authority` | 绑定来源和是否允许被覆盖 |

先按 `installation_id + bot_id` 筛选绑定，再在平台/账号命名空间内匹配。私聊按 `session` > `conversation + user` > `conversation` > `user` > `bot` > `installation`；群聊按 `session` > `conversation/group` > `bot` > `installation`，普通群消息不套用发言人的私聊 `user` 或 `group + user` 人格绑定。同一层内的 `precedence` 只处理显式优先级，同级同优先级冲突返回诊断错误。多人格群聊若需要按成员切换，应另设显式会话模式，首期不启用。

绑定变更递增 `persona_binding_revision`，仅使受影响绑定下尚未开始投递的候选、生成任务和动作令牌失效；已提交的动作进入回执对账，不能宣称取消已产生的外部效果。切回原人格恢复其持久状态，新请求使用新的绑定版本。

人格身份、关系状态和角色情绪必须分开：

- `persona_id` 决定“Bot 是谁”，同一会话的一次回复只能使用一个已解析人格；群聊中不能因为不同用户发言而隐式切换人格。
- `RelationshipProjection`、`AffectState` 和 `MotiveState` 的主键必须包含 `installation_id + bot_id + persona_id + target scope`。同一用户与不同 Bot 或不同人格的关系默认完全分开。
- 记忆、用户资料或身份映射只有在显式授权后才能跨 Bot/人格共享；跨平台的同一用户不能仅凭昵称或平台 ID 自动合并。
- `persona_calendar` 属于人格，`user_calendar` 属于用户；群聊日历和私聊日历不能互相覆盖。

插件实现必须遵守以下运行规则：

1. 模块级入口可以持有安装级服务容器、注册表和连接管理器，但不能保存隐式“当前用户/人格”。可变对象必须声明所有者、隔离键和生命周期；账号连接不按每个会话重复创建。
2. 每个回调、事件和能力调用都接收已解析的 `RuntimeScope`；缺少作用域时拒绝处理或返回 `scope_required`，不能使用“当前用户/当前 Bot”全局变量兜底。
3. 能力描述可以在安装级注册一次，但实际提供方、凭证、任务、速率限制和资源预算按 Bot 账号或会话实例隔离。
4. Supervisor 按资源所有者登记任务；主动队列、InteractionLedger 和审计按调用及目标关联。关系预算按 Bot/人格隔离，账号限流和安装总预算按资源归属共享，不能因切换会话或人格绕过总额度。
5. 管理员执行跨作用域汇总时必须显式声明 `scope_selector`，经过授权、脱敏和审计；普通插件不得遍历安装级全部用户或人格状态。

作用域预算采用分层限额：安装级限制总资源，Bot 级提供公平调度，人格/会话级限制局部并发。单进程无法保证绝对性能隔离；耗时 CPU 工作应离开事件循环，取消不能终止的外部进程需要进程级回收。

### 3.2.2 调用上下文与数据归属

`RuntimeScope` 用于授权、路由和判断当前调用是否过期，不直接作为所有领域表的主键。领域记录使用稳定的 `owner_key`，保留来源调用的引用；`persona_binding_revision`、临时 `session_id` 和提供方 `generation` 只参与请求校验、缓存失效与任务 fencing，不进入长期实体身份。

| 数据 | 稳定归属 | 会话变化时的行为 |
| --- | --- | --- |
| `PersonaWorldModel`、`HabitModel`、`PersonaContinuityState`、人格生活、日历、基线 | `installation + bot + persona` | 同一人格跨窗口共享自身生活；不能携带其他用户的私密内容 |
| 用户/群日历、资料、长期记忆、关系 | `installation + bot + persona + subject_ref + visibility_namespace` | 按领域授权复用；群与私聊默认不同命名空间，跨账号身份须先建立授权映射 |
| 当轮情绪、提示词缓存、主动机会 | 上述归属加会话/目标、用途；缓存另含相关 revision | 临时状态隔离；历史与长期关系不因开新线程而重置 |
| 账号连接、设备连接、媒体会话 | `installation + provider + account/device/session` | 按连接所有者复用；通过 ACL 授权给调用方 |
| 安装配置、能力注册 | `installation + extension` | 不需要伪造用户或人格才能管理 |

`subject_ref` 必须带平台/账号命名空间或已授权的统一身份引用，不能只保存裸用户 ID。每个领域明确哪些维度参与归属及唯一约束，再使用规范化结构生成键，禁止字符串随意拼接。用户日历这里指陪伴侧的授权视图；外部日历原始记录仍由来源服务拥有。

控制面和没有聊天目标的设备观测使用声明的安装/账号/设备作用域；Kernel 根据订阅和授权为每个消费方解析独立的 `RuntimeScope`。无法解析接收者时保留为提供方事实或返回 `scope_unresolved`，不能选择最近活跃用户兜底。

当前 `companion/injection.py` 的 `scope_key` 会散列包括绑定 revision 在内的全部字段，可继续用于兼容请求指纹；新的稳定 `owner_key` 需要单独引入和迁移，不能原地改动已有键的含义。

### 3.3 AstrBot 宿主改造策略

第一阶段不修改 AstrBot 核心。现有插件入口、生命周期、`get_registered_star` 和 `register_web_api` 足以让陪伴插件在自身内部实现 `ExtensionRegistry`、DTO 转换和兼容适配器。这样可以先验证协议，不把尚未稳定的设计变成宿主级约束。

后续只有在内部协议经过多个真实扩展验证后，才考虑向 AstrBot 提交小型、向后兼容的 PR：

| 宿主能力 | 优先级 | 作用 |
| --- | --- | --- |
| 标准插件能力清单接口 | 高 | 统一读取插件 ID、版本、能力和依赖，减少模块扫描 |
| 正式插件加载/卸载通知 | 高 | 处理热重载、失效实例和能力撤销 |
| 宿主任务托管接口 | 中 | 统一取消、统计和限制扩展后台任务 |
| 权限声明与授权接口 | 中 | 让权限由宿主/管理员授予，而非插件自行声称 |
| Workspace 页面注册机制 | 低/中 | 统一扩展页面外壳、鉴权和分页 |

不以一次大型重构的方式修改 AstrBot 事件模型、消息链或插件加载器。每个 PR 都必须保留旧插件行为，并能在没有陪伴插件时独立工作。

### 3.4 控制面和数据面的实现边界

主陪伴插件的控制面负责扩展发现、manifest 校验、版本协商、启停状态、能力状态、依赖、权限、作用域绑定、任务监督、资源预算、统一诊断和工作区展示。外部插件的数据面负责领域算法、外部连接、凭证、领域数据库、缓存、媒体处理和具体动作执行。

就扩展控制面而言，主陪伴只保存 `ExtensionManifest`、`ExtensionStatus`、能力描述和审计摘要，不保存扩展的账号密码、原始健康数据、精确位置或领域数据库；陪伴自身的领域状态仍按 3.6 保存。小型事实和结果通过 DTO 传递；媒体和大批量日志通过资源引用、会话引用或分页游标传递。

这种设计可以让主要代码和功能留在各自插件中，同时保持主陪伴对整体生命周期和 AI 上下文的统一管理。但它不是安全沙箱：AstrBot 插件仍运行在同一 Python 进程中，协议无法阻止恶意代码直接访问文件、网络或其他模块。

### 3.5 主要隐患与强制防线

- **权限越权**：manifest 只能声明所需权限，不能自行授予权限；设备、位置、健康、消息发送和付费后端必须经过用户/管理员授权。
- **作用域泄漏**：所有 DTO 必须带 `Scope`；群聊、私聊、人格和设备数据不能隐式跨域读取。
- **隐私过度注入**：精确坐标、原始生理数据和原始媒体默认先经过语义化和最小化，再进入角色扮演上下文。
- **热重载残留**：卸载时必须取消任务、撤销能力、使旧动作令牌失效，并拒绝旧实例回写。
- **资源放大**：图片、音频、视频、录屏和日志不能直接进入事件总线；必须有大小、TTL、并发和背压限制。
- **主动反馈环**：动作回执产生的状态事件必须携带来源、幂等键和冷却信息，避免“执行动作 → 状态变化 → 重复主动动作”。
- **版本碎片化**：按能力版本协商，而不是只判断插件版本；不兼容时明确标记 `unavailable` 或 `degraded`。
- **提示词污染**：外部插件只能提交带证据和优先级的 `ContextContribution`，不能直接注入任意 system prompt。

权限、作用域、幂等和任务取消属于协议必需项。首期在插件内记录资源用量，并依据现有用户/管理员授权做校验；宿主标准授权接口和进程隔离可后续增强，不作为基本校验的前置依赖。

### 3.6 状态和存储

- 陪伴核心可使用一个安装级 SQLite 数据库，领域表由各自服务拥有，Kernel 仅拥有控制面和协调账本；外部插件继续拥有自己的数据库。首期不要求跨插件合库。
- 大文件、图片、音频、视频和导入包使用内容寻址文件存储，数据库只保存元数据与引用。
- 每个 Feature Service 只能写自己的命名空间；跨域写入必须通过事件或 Kernel 用例完成。
- 核心迁移完成后，JSON 主要用于配置、导入、导出和迁移，不再承担跨插件共享可变状态；外部插件可保留内部格式，无需为接入协议立即更换数据库。
- 所有写入采用事务、revision 和幂等键；后台保存统一由 Store 管理器调度。
- 领域主键使用 3.2.2 定义的稳定归属；运行时指纹、绑定 revision 和资源 generation 独立保存，用于校验和追踪。
- SQLite 写事务保持短小，事务内不等待网络、LLM 或设备；使用有界写队列、忙等待超时和明确失败返回，不无限重试数据库锁。

#### 3.6.1 跨服务一致性与撤回

需要恢复的领域变更与 outbox 事件在所有者的同一本地事务中提交。消费者以 `event_id + consumer_id` 去重，并按实体 revision 更新投影；内存 EventBus 仅负责分发，不承诺持久化或全局顺序。跨库操作采用幂等命令、回执和对账，不宣称拥有分布式原子事务。

事件携带 `correlation_id`、`causation_id`、实体 ID、revision 和来源证据引用。晚到事件只更新仍适用的投影；修订/撤回事件使旧贡献失效后重算，重放不能再次触发外部动作。反压按来源与类型处理：可合并的状态观测保留最新值，承诺、撤回和动作回执进入可恢复队列，不能静默丢弃。

删除或撤回由数据所有者发起，并传播到索引、缓存、余波和待执行候选；审计只保留必要的操作元数据与不含正文的 tombstone。恢复备份后、开放查询前重新应用删除记录，防止已删除内容复活。各存储明确保留期限和备份失效策略，“可追溯”不等于无限保留原始内容。

#### 3.6.2 记忆精度与答案证据

针对“记得多但记不清”的源码审查与离线反例见[记忆精度专项审查](../../astrbot_plugin_remember_you/docs/MEMORY_PRECISION_REVIEW_20260906.md)。已复现可变事实粗粒度折叠、词语重合误判支持、注入截掉答案、权限过滤前全库候选挤占、摘要证据过期和 MRR 漏算未命中；这些是当前实现的具体路径问题，尚未修复，也不代表全部用户故障的发生率。

首期记忆能力在现有 MemoryRecord 上渐进增加断言与证据语义：主体、具体属性、值、否定、限定条件、有效时间、来源和修订关系。经历摘要用于可读回忆，不能代替精确事实。家庭地址和公司地址分别保存；历史值与当前值按问句时态选择；有歧义的修订保留冲突，不能仅凭类别相同就覆盖。抽取优先通过提示词保留语义和逐断言引用，结构检查负责引用、权限与 revision，有矛盾时按需复核。

召回在合法可见空间内生成候选，再选择当前问题需要的完整断言与证据片段，以 `AnswerEvidence` 交给核心编排。固定分槽和单条前缀截断不得成为答案细节丢失的默认机制；分别记录候选命中、断言选择、最终注入和省略原因。未安装记忆插件时正常降级，核心不维护第二套长期记忆。

长期有效断言保留获授权的最小证据片段，其生命周期独立于整段聊天日志；删除/撤回按 3.6.1 传播。旧引用已不可解析时标记 `source_missing`，不能凭摘要补造原话。日历、创作、观测与会话插件继续拥有各自事实权威，记忆保存带来源的断言和经历；同一事件的模型转述不算独立佐证。

反馈区分曝光、模型使用、用户确认、纠正与独立证据，注入次数不代表事实正确。首期以最终证据覆盖率、回答断言正确率、无依据细节率和补检索成本共同验收；候选 Recall/MRR 仍保留，但 MRR 必须计入未命中的零分。断言与 `AnswerEvidence` 是待适配契约，字段草案见注入协议 6.4，不表示当前 SDK 已实现。

### 3.7 日历和日程

日历是事实源，日计划是投影：

- `TemporalRecord` 表示事件、重复规则和例外，使用绝对时间和显式时区。
- 用户确认、外部课表/班表/预约、设备提醒和已执行回执分别标记 authority/evidence，不互相冒充。
- `daily_plan` 只保存某日的可执行建议和生成快照，不能反向覆盖日历事实。
- 运行时通过 `CalendarProjection` 生成当前窗口、下一窗口、跨日状态和提示词上下文。
- 计划允许“空闲、弹性、取消、延后和未知”状态；模型只能提出候选，确认和执行由策略与动作回执完成。

目标路径不会因为到了零点、插件启动或一次刷新，就自动生成一份覆盖全天的活动清单。`daily_plan` 在目标模型中只是按需重建的投影或兼容快照；它不能作为主动触达队列、角色经历或下一轮提示词的完整剧本。

#### 3.7.1 从“日程规划”转向“生活过程模拟”

日程不能成为角色生活的主生成器。真实生活通常由现实承诺、长期习惯、目标、身体/情绪状态、环境和即时互动共同产生；完整的一天不会在月初被确定。系统应保存稀疏的事实和倾向，在运行时生成当前活动，事后再形成活动记录和日程投影。

核心对象调整为：

| 对象 | 语义 | 是否为事实源 |
| --- | --- | --- |
| CalendarCommitment | 已确认的会议、课程、预约、交通和其他现实约束 | 是 |
| Routine | 作息倾向、重复习惯、活动窗口和可接受变化 | 否，属于长期规则 |
| Goal/Project | 创作、学习、运动、旅行等长期目标或阶段场景 | 否，属于意图 |
| LifeState | 睡眠压力、精力、情绪、社交欲、疲劳和当前环境 | 由观测和运行时状态组成 |
| ActivityEpisode | 已观测或内部模拟中开始、暂停、完成、取消或未知的一段活动 | 是，必须区分现实观测与角色模拟 |
| ScheduleProjection | 面向页面、主动系统和模型的当前/未来短期视图 | 否，随时可重建 |

月度和季度内容只保存生活阶段、节律变化、长期目标和关键锚点。例如“暑假”改变可用时间、睡眠弹性和出游倾向；“出游”保存交通/住宿等已确认锚点以及候选活动，不提前生成所有日程。

活动选择使用“需求竞争”模型：候选活动根据身体需求、目标相关性、习惯权重、环境适配、用户互动、活动成本、最近重复度和日历约束评分，再由行为策略选择下一段活动。固定承诺由确定性约束保护，软活动允许延后、缩短、跳过、替换、被打断和恢复。有限随机性用于产生自然变化，但必须按人格、生活阶段和日期稳定，以便复现和诊断。

起床、入睡、吃饭、发呆和自由时间都是运行时状态或活动，不是每天固定触发的报时事件。只有用户明确设置的提醒或现实中的硬承诺，才可形成必须执行的时间锚点。系统必须保留空闲、未知和临时活动，不能为了填满日历而编造经历。

#### 3.7.1.1 天气不是日程生成器

天气、空气质量、温度和预警属于 `external_observation`，不是日历事实，也不是角色一天的主线。天气信号至少带 `valid_from`、`valid_until`、严重度、置信度、修订号和去重键；它们先投影到 `EnvironmentContext`，再由活动选择和主动策略使用，不能直接创建全天 `CalendarCommitment` 或覆盖整份 `daily_plan`。

天气变化只触发局部影响分析：找到受影响的活动窗口、过渡段和缓冲段，重算这些局部候选，其他时间保持原状。软活动可以改为室内替代、缩短、延后、跳过或等待用户选择；现实承诺不能因天气观测自动改期。只有用户确认或已授权的规则，才能把替代方案写回日历，且必须生成新的 revision 和 ChangeSet。

天气可以产生一个带 `preferred_window`、`expires_at` 和证据的候选，例如“下午散步窗口可能下雨，临近时考虑室内活动”；候选不是消息，也不是预先排好的全天剧本。预测更新时，旧候选被 supersede 或过期，不重写当天已经完成、已确认或不相关的活动。PromptCompiler 只向模型提供受影响窗口和必要的环境摘要，不提供“根据天气生成整天安排”的自由入口。

长期计划和实时互动通过局部重算衔接：事件先判断影响范围，只更新当前活动、当天剩余窗口或受影响的计划子树；已完成记录、现实承诺和用户确认事项保持不变。每次调整保存原因、证据、前后版本和回滚信息，使角色能够表达“原本打算做什么、后来发生了什么、为什么改变”。

角色扮演上下文只注入当前活动、近期经历、下一项高置信意图、可用时间和必要的生活状态。计划意图、用户确认、设备观测、角色内部模拟和模型推测必须分级，角色不得把意图说成已完成的现实行为。

#### 3.7.1.2 局部前视而非整天大纲

新框架的默认规划单位是“当前需要决定的局部”，不是“今天的完整故事”。`PlanningHorizonPolicy` 根据当前活动、下一次转折、固定承诺、截止点和受影响窗口，按需生成有限的前视内容：

1. 当前活动段及其状态；
2. 下一项高置信转折或固定承诺；
3. 受当前事件影响的一个或少数候选窗口；
4. 必要的缓冲、空闲或未知状态。

前视窗口随事件和资源动态调整，不以固定的全天条目数为完成条件。用户主动要求“看看今天安排”时，可以从 `CalendarCommitment`、`Routine`、`Goal` 和已记录的 `ActivityEpisode` 现场渲染一份视图；视图中的软计划、模拟活动和未知项必须保留来源与状态，不能因为被展示就变成承诺、经历或主动消息。

兼容迁移期间，旧 `daily_plan` 可能继续由旧路径生成，以保证旧页面和旧命令可用；这只是回退/读取边界，不代表新框架的行为。新路径不得把旧计划中未经确认的条目当作当前事实、主动触发器或必须完成的任务，也不得因整天计划中出现了某项活动就预生成图片、语音或消息。迁移完成后，旧全天生成器应退役，保留的只是可按需重建的投影。

因此，以下行为属于目标设计的失败：启动时为每个时间段生成完整 `today_events`；要求每段必须有主动契机；把未发生的吃饭、散步或拍照写成已完成经历；或从全天大纲逐项派生主动消息。只有用户明确的现实承诺、授权提醒和已记录的实际回执可以跨越当前窗口保留。

#### 3.7.1.3 从“时间页”到角色连续生活状态

`ScheduleProjection` 和每轮的 Prompt 快照都会过期，但角色的生活不能随页面翻页一起消失。新框架增加由陪伴核心拥有的 `PersonaContinuityState`：它是从日历事实、活动经历、用户互动、目标和动作回执持续投影出的中期生活状态。日程是这个状态的一个来源和视图，提示词只是它的一个消费者。

| 层 | 保存内容 | 生命周期 | 用途 |
| --- | --- | --- | --- |
| `ActivityEpisode` | 一段活动的开始、暂停、完成、取消、偏离和 `observed|simulated` 证据 | 追加记录，可修订/撤回 | 说明角色实际经历过什么，供后续状态重建 |
| `PersonaContinuityState` | 当前活动引用、未完成事项、进行中的目标、重复形成的偏好、近期经历引用和待处理念头 | 跨时间段，按字段分别过期 | 影响下一段活动选择、动机、表达和主动候选 |
| `ScheduleProjection` | 当前段、下一转折、固定承诺和受影响窗口 | 按需重建 | 页面、调度器和模型的短期视图 |
| `PromptSnapshot` | 本轮经过权限和裁剪的连续性摘要 | 单轮/短 TTL | 只服务本次扮演，不反向成为事实 |

状态更新采用“事件 -> 状态变更提议 -> 校验/提交 -> 新 revision -> 投影”的路径：

~~~text
CalendarCommitment / Routine / Goal / Interaction / Observation / ActionReceipt
  -> ActivityEpisode 或 DomainEvent
  -> StateTransitionProposal
  -> owner、证据、权限、revision 和 TTL 校验
  -> PersonaContinuityState revision + outbox
  -> ActivitySelector / MotiveProjector / PromptCompiler / ProactiveEngine
~~~

`PersonaContinuityState` 至少覆盖 `state_revision`、`current_activity_ref`、`open_loops`、`ongoing_goals`、`routine_drift`、`recent_experience_refs`、`pending_intentions` 和 `last_transition_at`。它不保存模型生成的整段生活旁白；长文本经历交给记忆服务，情绪余波交给 `AffectResidue`，现实用户事实仍由各自事实源拥有。状态投影失败时保留上一份有效 revision，不能用空白或新一页大纲覆盖角色连续性。

持久化必须按语义分层：未完成的目标、承诺偏移、重复验证后的偏好和关系后果可以跨日保留；当前饥饿、天气、临时想法和一次性可分享内容带 TTL；已经撤回或被证据否定的经历通过修订失效。这样“昨天散步没走完”可以成为今天的开放事项，“昨天想发一张饭照”不会永久变成待发送任务。

角色扮演不再只读取日程文本，而是读取经过裁剪的 `ContinuitySnapshot`。同一状态同时供活动选择、动机投影、表达姿态、主动调度和记忆写入判断使用；其中只有与当前问题有关的部分进入 Prompt。新消息、活动完成、活动偏离、用户确认和动作回执都可以产生状态变更，因此日程对角色的影响会跨越当前回复继续存在。

现有“技能”若只添加一个提示词片段、返回一次命令或写入一页日程，仍然是浅层接入。新框架中的 `Skill/Capability` 应至少能声明自己的观察或动作，发布带证据的领域事件，提出受限的 `StateTransitionProposal`，并消费连续性快照决定下一步；它不能直接改人格核心、拼接永久 system prompt 或发送消息。技能是否改变角色，应由事件证据、状态策略和后续 revision 决定。

例如角色原计划去散步，后来与用户边走边聊，途中又到了吃饭时间：散步的 `ActivityEpisode` 可以记录为进行中或被中断，精力和“稍后继续”的开放事项进入 `PersonaContinuityState`，吃饭作为角色内部经历保留。当前时间页结束后，这些状态仍能影响下一次回应和活动选择；饭照候选仍受对话占用态和用户请求约束，不会自动发出。

#### 3.7.1.4 具身世界模型、长活动和习惯

真正的拟人需要一个可持续、可查询、可修订的 `PersonaWorldModel`。它模拟的是角色所属的生活世界，不是把更多动作描写塞进提示词。世界模型只属于对应人格；现实用户的房间、衣物、健康和位置仍由授权的外部事实源拥有，外部观察不能无条件覆盖角色的模拟事实。

世界模型至少分为以下层次：

| 对象 | 保存内容 | 生命周期/证据 | 对行为的影响 |
| --- | --- | --- | --- |
| `WorldEntity` / `WorldRelation` | 房间、家具、设备、衣物、食材、常去地点、路线节点及其关系 | 人格范围内持久保存；每项带来源、`reality_mode`、revision 和可见性 | 决定可用资源、场景连续性和动作可行性 |
| `EmbodimentState` | 当前所在位置、姿态、注意力、精力、饥饿、清洁感、穿着、携带物和身体限制 | 高频变化的状态快照；字段分别设置 TTL | 影响能做什么、表达负荷和下一活动选择 |
| `ActivityProcess` | 刷手机、安静学习、洗澡、吃饭、散步等活动的阶段、进度、预计时长、可打断性和恢复方式 | 活动期间持有，结束后形成 `ActivityEpisode`；中断和恢复可多次发生 | 让长活动跨越多个时间段并保持因果连续 |
| `HabitModel` | 洗澡时长分布、食物偏好、路线权重、衣物选择倾向、学习节奏和触发条件 | 跨日积累，按上下文、证据量和置信度更新 | 为活动选择和表达提供倾向，不变成固定脚本 |
| `AffordanceSnapshot` | 当前可用的物品、地点、动作、剩余时间和阻碍 | 按请求/短 TTL 重建 | 供活动选择、技能和 Prompt 使用，不暴露整张世界数据库 |

长活动不能被拆成一连串报时消息，也不能由每分钟一次的 LLM 调用维持。`ActivityProcess` 至少包含 `process_id`、`kind`、`phase`、`started_at`、`progress`、`duration_distribution`、`attention_mode`、`interruptibility`、`resume_policy`、`next_checkpoint_at`、`effects`、`reality_mode` 和 `source_refs`。系统只在用户互动、承诺边界、外部观测、主动评估或检查点到达时推进它；没有事件时保留状态和下一次唤醒时间。

习惯使用“带上下文的倾向和分布”，不使用单一硬编码值。例如：

- 洗澡通常为 8--15 分钟，疲劳、天气和是否洗头会改变分布；
- 早餐偏好清淡面食，但库存、时间和近期重复度会影响选择；
- 散步路线按时间、天气、拥挤程度、心情和共同活动权重选择；
- 衣柜记录衣物的拥有、可穿、待洗、收纳和缺失状态，穿过的衣物会影响下一次搭配。

每条 `HabitModel` 至少记录 `context`、`preferred_options`、`avoid_options`、`duration_distribution`、`confidence`、`evidence_refs`、`revision` 和 `expires_at`。重复的真实或角色经历只能在达到最小证据量后改变倾向；用户明确纠正立即建立新 revision。没有证据的衣物、路线、口味和习惯保持 `unknown`，不能为了让世界看起来完整而补齐。

世界状态通过事件和状态变更持续演化：

~~~text
WorldEntity / HabitModel / ActivityProcess
  + CalendarCommitment / Routine / Goal / Interaction / Observation / ActionReceipt
  -> WorldEvent / ActivityEpisode
  -> StateTransitionProposal
  -> PersonaWorldModel + EmbodimentState + PersonaContinuityState revision
  -> ActivitySelector / MotiveProjector / AffordanceSnapshot / PromptCompiler / ProactiveEngine
~~~

`PromptCompiler` 只注入当前需要的世界片段，例如“正在安静学习、桌上有水、预计还有一小时可用”，不注入衣柜全量清单或整段生活史。世界状态会同时影响活动选择、可执行动作、关系表达、主动候选和记忆写入判断；回复只是其中一个出口。

现有技能应升级为世界能力提供方：查询或更新物品/路线/习惯，推进活动过程，发布带证据的 `WorldEvent`，提出受限状态变更，并返回动作回执。技能不能用一次调用直接创造长期事实，也不能把生成图片、动作旁白或 Prompt 片段当成世界变化。模拟世界可以很丰富，但所有对象都必须能回答“来源是什么、当前是否有效、何时过期、谁可以看到”。

例如“安静学习”可以从 19:00 开始，经历专注、短暂分心、喝水和恢复几个阶段；用户中途发来消息时，活动根据 `interruptibility` 决定暂停或保持背景运行，回复完成后从原进度继续。第二天系统仍可知道这次学习是否完成、哪些内容未完和下一次更容易进入专注的条件，而不需要保存一整天的逐分钟剧本。

#### 3.7.2 时间段级双向决策

日历不应只按“今天有什么”提供摘要，而应按当前时刻解析一组有边界的时间段。时间段可以重叠，并且具有优先级、来源、确定性、可打断性和状态：

| 时间段类型 | 作用 |
| --- | --- |
| commitment | 会议、课程、预约、交通等现实承诺 |
| activity | 当前或计划中的工作、休息、创作、陪伴和出行 |
| availability | 可聊天、可执行任务或可接受主动触达的窗口 |
| quiet | 睡眠、专注、免打扰或用户明确禁止触达的窗口 |
| transition | 通勤、准备、收尾和恢复等过渡时间 |
| deadline | 截止时间或必须在此之前完成的窗口 |
| buffer | 为延迟、交通和意外保留的缓冲 |
| unknown | 时间存在但事实或计划尚未确定 |

Kernel 为每一轮对话和每个主动候选生成 TemporalDecisionContext，至少包含当前活动段、未来转折点、下一项固定承诺、可用窗口、冲突、截止时间、当前时间段策略、对话占用态和来源证据。模型不需要读取整张日历，只接收与当前决策相关的时间段。

日历与 Bot 形成双向控制回路：

~~~text
日历事实/时间段变化
  -> 解析当前决策上下文
  -> 影响回复、主动触达、动作和活动选择
  -> Bot 产生观察、活动更新或日程调整提议
  -> 权限和冲突策略检查
  -> 用户确认或授权范围内自动提交
  -> 写入日历并发布事件
~~~

Bot 对日历的写入使用以下命令与授权流程；observe/suggest/reserve/commit 的权限层次见下文。

Bot 的日历控制必须通过结构化 CalendarCommand 完成，不能让模型直接输出自然语言修改数据库。命令至少包含目标记录、操作类型、时间段补丁、原因、证据、作用域、预期 revision、授权来源和幂等键。支持的操作包括 create、move、resize、split、merge、postpone、cancel、complete、reserve、lock 和 unlock。

执行采用预览/提交两步：

~~~text
模型提出 CalendarCommand
  -> 校验作用域、权限、时间格式和预期 revision
  -> 计算受影响的时间段、冲突和替代方案
  -> 生成 CalendarChangeSet 预览
  -> 按授权策略自动提交或请求用户确认
  -> 事务写入新 revision
  -> 发布 calendar.changed 事件
  -> 刷新 TemporalDecisionContext
~~~

必须分离两类日历：

- persona_calendar：Bot 自己的模拟生活、习惯、内部活动和角色目标；在用户授权的拟人化范围内可以自动调整；
- user_calendar：用户现实中的会议、课程、预约、交通和设备提醒；创建或修改现实承诺默认需要用户确认，外部日历同步还需要单独授权。

自动控制只允许作用于已授权事项，例如移动软活动、缩短休息前的创作、插入共同活动或释放过期预留。涉及固定承诺、改变提醒、跨越安静时段或外部动作时，重新校验具体授权；已有授权覆盖该操作、目标和时间范围时可以执行，超出范围才请求确认。内部日历调整不自动授予设备、付费或第三方写入权限。每次调整保留旧版本和 ChangeSet，Bot 只能根据提交成功后的回执描述结果。

1. observe：记录实际开始、暂停、完成、取消和偏离；
2. suggest：提出候选时间段或调整，不改变事实；
3. reserve：在用户授权范围内暂时占用弹性窗口，带过期时间；
4. commit：创建或修改现实承诺，只能在明确授权或用户确认后执行。

日历对 Bot 的控制也分为四级：

1. context：提供当前场景和未来时间段；
2. preference：影响活动排序、表达方式和主动强度；
3. constraint：禁止冲突、保护睡眠、限制打断或要求在截止时间前完成；
4. gate：在用户确认、权限或现实回执缺失时阻止动作执行。

时间段的变更必须使用局部影响分析：先锁定已完成和已确认事项，再只重算受影响的活动、过渡段和缓冲段。任何自动调整都要记录原版本、新版本、原因、证据、授权来源和回滚信息，防止 Bot 与日历互相触发无限调整。

时间段级决策不能等同于定时器。时间段提供的是“现在适合做什么、什么不能做、多久后会变化”的约束和机会；是否主动说话、采用何种角色表达以及是否执行动作，仍由人格、关系、权限和主动策略共同决定。

#### 3.7.2.1 对话占用态覆盖

`availability` 只表示“是否可能接受联系”，不表示“可以在当前对话旁边插入另一条消息”。为避免日历把可用窗口误当成插话许可，Kernel 在 `TemporalDecisionContext` 上叠加按会话/目标计算的 `ConversationOccupancy`。它是由当前轮次、最近双向消息、线程连续性、用户收束信号和投递回执推导的短期状态，不写入用户日历，也不改变人格生活事实。

最小状态和处理方式如下：

| 对话占用态 | 进入条件 | 主动行为处理 |
| --- | --- | --- |
| `turn_open` | 用户新消息已进入，当前回复尚未完成或尚未落账 | 所有普通候选只允许合并到当前回复或暂存；不启动旁路投递和无关媒体。经授权的 `alert`/安全事件才可用最短表达抢占 |
| `engaged_thread` | 同一 `thread_id` 内持续双向交流，或用户明确表示继续当前话题 | 同主题候选合并到当前回复；`ambient`、`share`、`invitation` 等无关候选延后到线程收束/空闲，不发送角色生活图片。明确预约的提醒保留待处理状态，按其时效策略排队 |
| `closing` | 用户告别、话题收束，或连续互动后进入短暂收尾窗口 | 维持短暂的低打扰宽限；可将摘要或相关分享并入收尾回复，其他候选等待 `idle` |
| `idle` | 没有正在占用的线程，且不处于 `quiet` | 按日历窗口、主动策略和接触预算正常竞争 |
| `quiet` | 用户明确免打扰、睡眠或策略禁止触达 | 普通候选硬门禁；只有授权的安全/现实承诺流程可例外 |
| `unknown` | 缺少可靠的线程或用户状态证据 | 不猜测用户空闲；低价值候选延后，直接请求仍正常响应 |

`ConversationOccupancy` 至少携带 `state`、`conversation_revision`、`active_thread_id`、`topic_fingerprint`、`last_user_turn_at`、`last_bot_turn_at`、`continuation_until` 和 `source_refs`。它按 `RuntimeScope + conversation_id + session_id + target_scope` 隔离，并在每次用户消息、回复落账、取消、切换人格和卸载时递增 revision。候选或投递计划引用旧 revision 时，必须重新判断，不能沿用“之前可发送”的结论。

日历中的活动和对话占用可以同时存在。例如用户正在散步，日历可记录 `activity=walk`、`availability=available`，但只要聊天仍处于 `engaged_thread`，角色内部产生的“吃饭” `ActivityEpisode` 只能更新 `persona_internal` 状态或历史。它可以形成一个带 `defer_reason=conversation_busy` 的分享候选，却不能因为活动完成或图片生成成功就直接投递；只有当前话题询问饮食、用户明确要看，或线程收束后候选再次获准时，图片才可作为同一回复或后续机会出现。

对话占用态是短期决策覆盖，不是更多定时器。默认延续窗口、收束宽限和不同候选的打扰成本应作为可观测、可回滚的 `PolicyAsset` 配置；模型通过提示词获得当前状态和处理要求，只有 `turn_open`、明确 `quiet`、权限和安全等边界使用硬门禁。这样可以调节“聊得正好时不要插话”的灵敏度，而不会把所有主动行为永久关闭。

#### 3.7.3 时间与变更的最小语义

- 时间区间采用 `[start, end)`，相邻区间不算冲突；全天事项保存本地日期范围和 IANA 时区，不强制换算成固定 24 小时。瞬时截止点与持续时间段分开表示。
- 重复事项保存本地起始时间、时区、重复规则、例外及稳定的 occurrence ID；按有限查询窗口展开。优先复用成熟的 recurrence/ICS 库，明确夏令时缺失时刻与重复时刻策略，不以固定秒数推算每一天。
- persona 与 user 的日历分别计算冲突。`quiet` 区分用户明确免打扰与模型推测/模拟作息：前者按授权执行限制，后者用于提示词和时机评分，不能仅凭推测让用户的直接请求无响应。
- `ActivityEpisode` 携带 `reality_mode=observed|simulated` 和 `subject_ref`；内部模拟可以支撑角色生活叙述，但不能证明用户活动或现实设备操作已经发生。
- 用户确认绑定 ChangeSet 的目标、参数摘要、预期 revision 和有效期。等待确认期间事实变化则返回 `revision_conflict` 并重算预览，不能拿旧确认提交新方案。
- 本地提交成功与外部日历同步成功分别记录；外部同步为 pending/uncertain 时如实表述。撤销已同步事项是新的补偿命令，需要重新校验版本和授权，不能只恢复本地快照。
- 旧 `daily_plan` 仅能迁为意图或历史快照；缺少完成证据的项目不能批量升级为现实承诺或已完成经历。

### 3.8 任务和资源

Kernel 的 `TaskSupervisor` 监督已接入任务的创建、命名、取消、等待和结果。扩展可以托管现有任务句柄或在受监督的任务组内创建子任务。每个任务声明所有者、作用域粒度、能力、最大并发、超时、重试/退避和资源预算。

长连接和轮询可以保留必要循环，但必须具备取消点、退避、关闭句柄和父任务归属，不能再维持未登记的第二套调度。卸载先撤销准入并递增 generation，再取消与等待子任务，最后关闭资源；超时任务标记失败并隔离旧回写。任务按安装、账号、设备或会话的实际生命周期结束，不因某个聊天窗口结束而关闭共享账号连接。

### 3.9 页面

- 管理体验统一为一个 Companion Workspace 外壳，Dashboard 与可选独立 WebUI 复用资源处理器和授权策略；不同入口保留各自的登录会话，不能互相信任任意请求头。
- Feature Service 注册管理模块和查询/命令。房间客户端、屏幕媒体流、直播字幕、移动网关等可以保留独立服务及交互页面，统一登记健康、访问票据与生命周期；高频媒体数据不经管理 Gateway 中转。
- 页面首屏只加载核心摘要；功能页按需加载，列表采用分页/游标，图片和日志使用缩略图与增量查询。
- API 按 `scope -> feature -> resource` 命名，统一错误、能力不可用和权限响应。

配置区分“持久配置”和“当前运行状态”。设置继承按安装默认、Bot、人格、会话的适用范围解析，页面同时返回有效值、来源和 revision；显式关闭不被默认值覆盖。写入携带预期 revision，发生并发冲突时显示差异，不以最后写入静默覆盖。跨扩展批量保存返回逐项结果，不宣称跨数据库原子成功。

### 3.10 提示词与事实约束

LLM Gateway 接收结构化上下文和 `PromptPolicy`，负责上下文裁剪、缓存前缀、预算、模型路由、JSON/文本校验和失败重试。领域模块只提供模板和约束，不直接拼接宿主私有上下文。

外部资料、用户陈述、模型推测、内部状态和执行回执必须有不同的 `evidence_kind`。提示词约束优先解决边界问题；硬编码关键词只用于协议解析和安全上限。

### 3.10.1 情绪状态、动机与表达调制

临时情绪插件的实验结果表明，角色的情绪不能只用一个 `mood_score`，也不能让每条消息直接覆盖上一条情绪。新架构吸收它的状态机思想，把事件、状态、动机、余波和输出拆开，并让每层只有一个所有者：

~~~text
AffectEvent       一次有证据的情绪影响
  -> AffectState  当前作用域内的短期情绪状态
  -> MotiveState   当前更想靠近、修复、休息、探索、关心或保持边界的倾向
  -> ThoughtSeedContribution / CandidateModifier / ExpressionPosture
AffectState --话题结束/每日结算--> AffectResidue  有限的情绪余波
~~~

#### AffectEvent：只记录“发生了什么影响”

情绪事件沿用 `companion_emotion_event.v1`，必须携带来源、作用域、目标归属、强度、置信度、正负价性、唤醒度、脆弱度、有效期、去重键和修订关系。`actor_ref`、`target_ref` 和 `quoted_target_ref` 用来区分“用户直接对 Bot 说”“用户在转述第三方内容”“用户自己遇到不顺”以及“对象不明”；对象归属不明确时只能产生低置信度或中性事件。

模型只负责从消息、记忆或外部观测中解释证据，输出事件类型和置信度；规则负责校验作用域、过期、权限、去重和安全边界。模型不得直接写入情绪分数、直接修改人格或调用发送接口。外部插件的情绪注入必须调用事件生产者能力，不能再调用一个裸的 `inject_external(user_id, emotion, score)`。

#### AffectState：短期、有惯性的投影

`AffectState` 由陪伴核心情绪领域的 `AffectStateProjector` 统一维护，按“人格 + 用户 + 会话/窗口”作用域隔离。核心保存有界的 `valence`、`arousal`、`vulnerability`、负荷、主导方向、恢复阶段和来源事件引用；具体的“开心、担忧、失望、害羞”等名称是可插拔策略标签，不成为 Kernel 的固定枚举。

投影策略吸收临时插件的以下经验：

| 机制 | 新架构做法 | 作用 |
| --- | --- | --- |
| 普通互动与重大事件分开 | `event_class`、证据等级和类型策略共同决定注入上限 | 夸奖、闲聊不会把状态瞬间推满，争吵、道歉、边界事件可以更强 |
| 多段阻尼 | `AffectProjectionPolicy.damping_curve` | 压低模型偶发的极端分数，让情绪逐步变化 |
| 个体易感性 | 人格/关系范围内的 `sensitivity_profile` | 同一事件对不同角色产生不同幅度，仍受全局上限约束 |
| 情绪影响图谱 | 版本化 `impact_graph` 或维度耦合矩阵 | 失望削弱期待、担忧削弱安心，同时允许“担心但仍然期待”并存 |
| 时间消解 | 每类状态的半衰期、恢复条件和高负荷加速衰减 | 避免情绪永久卡住，也保留短时间内的连续性 |
| 落差/冻结 | 作为有明确证据和 TTL 的 `contrast_shock` 状态 | 重大反转时暂时压低原有积极状态，问题解决或道歉后逐步恢复 |
| 安心/道歉/安抚 | 作为 `repair` 或 `reassurance` 事件减少负荷 | 不是简单正负相抵，保留适度残留和恢复过程 |

“泼冷水”、冻结和最低负面残留只能作为可替换策略，必须绑定事件归因、强度阈值和有效期。普通负面消息、歌词转述或模型低置信度误判不能冻结角色的全部正面状态。

#### AffectResidue：有限的情绪余波

短期状态达到“时间、强度、证据质量、话题结束和关系重要性”条件后，才生成 `AffectResidue`。余波只保存脱敏摘要、主导方向、有限的调制值、来源事件引用、作用域、保留期限和是否允许跨窗口使用；它不是每条消息的长期记忆，也不自动公开到 QQ 空间或其他渠道。

记忆插件可以负责余波的长期索引和检索，Kernel 负责当前状态和投影。跨窗口情绪默认只影响表达底色，不携带原会话正文；跨用户、跨平台或跨人格必须被作用域检查拒绝。临时情绪插件的“话头结束写情绪日记”迁移为 `AffectResidue` 生成器，不能继续直接写独立 JSON 日记并注入主提示词。

#### 三种决策输出

情绪既影响念头的产生，也影响最终行为，但两者通过不同 DTO 连接：

| 输出 | 影响阶段 | 示例 | 限制 |
| --- | --- | --- | --- |
| `ThoughtSeedContribution` | 念头/候选生成前 | `repair_need` 提高“解释或关心一下”的候选倾向；`share_drive` 提高分享内部活动的倾向 | 只增加或减少有限倾向，不能直接产生或发送消息 |
| `CandidateModifier` | 候选竞争与时机选择 | 降低打扰成本、提高连续性价值、限制追问、建议延后到可用时间段 | 只能在有界范围内改分和形式；不能改变权限、证据、优先级车道或接触预算 |
| `ExpressionPosture` | IntentPlan 到表达结果 | `safety_mode=boundary`、温度、距离、长度、是否追问、语音节奏和可用行为 | 只能输出结构化姿态，由统一 PromptSection 生成提示；不再由扩展直接拼 `system_prompt` |

情绪影响主动频率时，先通过 `CandidateModifier.readiness` 和 `ContactBudget` 的软评分体现；只有边界、安全、用户明确要求或无法保证幂等时才能硬阻断。这样“生气时不想主动”不会变成永久沉默，也不会绕过用户自己的频率设置。

#### 实验策略的归属

现有实验性功能按以下方式进入新架构：

| 现有实验 | 迁移后的角色 | 保留的有效经验 |
| --- | --- | --- |
| `astrbot_plugin_temp_emotion` | `AffectStrategyProvider`，先以影子模式运行 | 阻尼、事件分级、图谱联动、落差恢复、话题结束沉淀、边界优先和语义提示词 |
| `domains/affect/interaction_dynamics.py` | `AffectStateProjector` 的一套策略资产 | 互动档位半衰期、正负方向恢复和连续互动的渐进变化 |
| `domains/affect/reply_temperature.py`、`companion_interaction_expression.py` | `ExpressionPosturePolicy` | 关系档位、精力/日程调制、低能量短答、脆弱时少追问和安全上限 |
| `memory_companion` 的情绪事件与跨窗口余波 | `AffectResidue` 存储/消费适配器 | 事件可修订、投递游标、严格私聊归属、脱敏和 TTL |
| 边界反馈与情绪闸门 | `SafetyPosture` + 高优先级 `AffectEvent` | 越界事件优先于普通情绪判断，明确拒绝和冷却恢复 |
| QQ 空间情绪宣泄、群聊气氛、游戏/直播余波 | `CandidateProvider` 或领域 `ContextContribution` | 作为候选或场景素材参与统一调度，不能直接发布或改变情绪核心 |

以下内容不直接成为核心规则：固定的情绪名称/正负池、关键词表、每条私聊都调用远程 LLM、直接向 `on_llm_request` 追加情绪文本、情绪阈值自动写长期记忆，以及“负面达到某阶段就全面禁用主动”。这些可以作为可回滚的 `PolicyAsset` 或低置信度 fallback，必须通过事件证据、作用域、冷却和观测指标验证。

#### 迁移边界与验收

迁移期间由 `TempEmotionAffectProvider` 读取旧事件或快照生成新投影。影子阶段旧路径继续承担当前生产行为，新路径只计算与审计，不注入 prompt、不发消息、不写生产记忆或情绪状态。逐作用域切换时先交接写入与注入所有权，保证只有一条路径生效；旧路径保留为只读回退候选。指标达标且完成恢复演练后，按保留策略退役旧状态文件和重复入口。

验收重点不是情绪种类更多，而是：转述内容不会误伤角色；重大事件比闲聊有更大但有界的影响；道歉和安抚能产生可解释的恢复；情绪能改变候选倾向和表达姿态但不能越权发送；余波可追溯、可过期、可撤回；扩展卸载或模型不可用时主链仍能以中性姿态稳定运行。

### 3.10.2 情绪功能实现路线

情绪功能的实现目标不是让模型输出一段“内心戏”，而是让角色在每一轮都能稳定回答三个不同问题：**发生了什么影响我？我现在更想做什么？这次应该怎样表现？** 情绪主要改变在意程度、恢复速度和接触成本；动机主要决定念头方向；日历、关系、权限和主动预算决定哪些行为实际可行。三者都不能直接绕过 Kernel 执行动作。

#### 情绪流水线

```text
消息 / 记忆 / 日历 / 外部观测 / 动作回执
                    |
          AffectEventProducer
                    |
          AffectStateProjector
                    |
             MotiveProjector
          /          |          \
 ThoughtSeed   CandidateModifier  ExpressionPosture
     |               |                   |
 候选生成器       PolicyArbiter       PromptCompiler/TTS
          \          |          /
             DeliveryGateway
                    |
              FeedbackLedger
```

#### A. 事件生产和证据解释

1. 实现 `AffectEventProducer` 接口，接收主对话消息、记忆检索结果、日历变化、健康/环境观测和动作回执。每个提供方只提交证据，不提交最终情绪分数。
2. `AffectEvent` 必须包含 `scope`、`actor_ref`、`target_ref`、`event_class`、`valence`、`arousal`、`vulnerability`、`confidence`、`occurred_at`、`valid_until`、`dedupe_key`、`evidence_refs` 和 `trace_id`。
3. 本地规则校验作用域、显式引用关系、过期和去重。讽刺、争吵、转述、道歉等语义归因由现有语义结果或异步模型解释，提示词要求标出证据与不确定性；低置信度时保留上一有效投影或产生待复核事件，不能用关键词直接扣关系分或冻结状态。
4. LLM 只负责解释语义和证据，采用“普通互动抽样、重大事件即时复核”的异步策略。模型超时或 JSON 无效时丢弃本次解释，不阻塞主回复。

#### B. 状态投影和动机投影

1. `AffectStateProjector` 在事务中按事件版本更新 `valence/arousal/vulnerability/load`、主导方向、恢复阶段和来源引用；同一来源事实的检索、重放不能再次累加影响。语义修订以 `supersedes` 替换旧贡献后重算，撤回移除贡献；异步结果校验输入版本和 generation，过期结果不能覆盖新状态。
2. 普通互动、关系事件、边界事件和安全事件使用不同上限；阻尼、半衰期、易感性、影响图谱和恢复条件全部放入可回滚的 `AffectProjectionPolicy`。
3. `MotiveProjector` 将短期状态和当前时间段、关系状态、未完成承诺、用户近期回应合成为有界动机向量，例如 `connect`、`repair`、`rest`、`curiosity`、`care`、`boundary`、`expression`。
4. 动机向量是当前决策投影，不是人格改写，也不是必须完成的任务。情绪可以提高或降低某个动机的权重，日历和权限可以将其限制为不可执行。

#### C. 影响念头和候选

1. `ThoughtSeedContribution` 只描述“值得考虑的方向”，例如 `repair_need`、`share_drive`、`check_in` 或 `rest_preference`，并带证据、权重上限、有效期和允许的候选类型。
2. 候选生成器可以根据多个 seed 生成少量 `CandidateProposal`，也可以返回空结果。模型不得凭空把情绪解释成事实、承诺或用户需求。
3. `CandidateModifier` 只改变候选的 readiness、连续性价值、打扰成本、追问倾向和建议时间窗；不得改变权限、证据等级、车道、接触预算或发送状态。
4. 情绪造成的“暂时不想说话”只能降低 readiness 或缩短表达，除非是边界/安全事件，否则不能直接关闭所有主动行为。

#### D. 影响表达和多模态输出

1. `ExpressionPosture` 由关系、日历、当前情绪和动机共同生成，最小字段包括 `distance`、`warmth`、`directness`、`length_budget`、`question_budget`、`safety_mode`、`preferred_modality` 和 `tts_style`。
2. `PromptCompiler` 将姿态编译为短的结构化上下文，放入当前请求的动态区；稳定人格仍保持在系统提示词，快速变化的情绪数字不能破坏 Provider 前缀缓存。
3. TTS、生图、表情、分段等扩展只消费姿态和最终文本，不反向修改情绪、动机或主动优先级。动作结果必须回写 `ActionReceipt` 后才能产生后续情绪事件。
4. 输出生成失败时回退为中性姿态和文本；不得为了“表现情绪”生成未经证实的经历、身体症状或关系承诺。

#### E. 余波、记忆和日结

1. 话题结束、重大事件解决或每日结算时，由 `ResidueGenerator` 根据强度、持续时间、证据质量和关系重要性决定是否生成 `AffectResidue`。
2. 余波只保存脱敏摘要、主导方向、有限调制值、来源引用、作用域、TTL 和撤回关系；原始对话、健康值、精确位置和媒体不复制到 Kernel。
3. 记忆插件可以索引余波，但必须在召回时重新检查作用域、隐私和有效期。跨窗口余波默认只改变表达底色，不能自动产生跨窗口主动消息。
4. 日结只做确定性衰减、未完成动机整理和容量清理；模型日记是可选的表达结果，不能成为状态事实源。

#### F. 旧实验功能迁移

| 旧功能 | 新实现 | 首次接入方式 |
| --- | --- | --- |
| `astrbot_plugin_temp_emotion` | `AffectStrategyProvider` | 影子模式，只比较事件、状态和姿态差异 |
| `global_mood`/好感与情绪面板 | `AffectState` + `RelationshipProjection` | 读取旧状态生成快照，不直接覆盖新状态 |
| `interaction_dynamics`、`reply_temperature` | `AffectProjectionPolicy`、`ExpressionPosturePolicy` | 把阻尼、半衰期和表达档位登记为 `PolicyAsset` |
| 情绪思维链/`<thought>` 展示 | `ThoughtSeedContribution` 调试视图 | 只向管理员展示结构化摘要，不写入聊天历史 |
| QQ 空间、群聊、游戏、直播情绪 | 领域 `SignalSource` 或 `ContextContribution` | 先作为候选素材，禁止直接发布或修改核心情绪 |
| 健康、屏幕、环境对角色状态的影响 | `ObservationSignal` -> `AffectEvent` | 仅传递最小语义摘要，并遵守独立授权 |

  迁移顺序固定为：**事件只读接入 → 状态影子投影 → 动机和候选预览 → 表达姿态预览 → 受控用户灰度 → 旧入口退役**。任何阶段都保留 `legacy-compatible` 策略版本和回滚快照。

### 3.10.3 市场实践参考与拟采用路线

新架构拟采用“**事件账本 + 分层投影 + 低频语义分析 + 统一决策调制**”路线。下面的外部项目映射是机制参考，尚缺逐项仓库 URL、commit 和行为验证记录，不能据此认定其实现已经验证稳定；先按本项目既有行为建立对照。

**核心选型**如下：

| 参考项目 | 参考内容 | 在本项目中的拟落点 |
| --- | --- | --- |
| `emotion_state` | 有证据的情绪事件、事件生命周期、阻尼、半衰期、低频异步 LLM | 作为 `AffectEventLedger`、`AffectStateProjector` 和 `AffectProjectionPolicy` 的主要参考 |
| `AstrEmbodiment` | 证据与状态分离、原子提交、受限表达投影、只读观测 | 所有状态变更先形成可校验投影，再一次性提交；表达只能消费 `ExpressionPosture` |
| `CompanionLite V2` | `observe -> active` 影子运行、关系证据与表达姿态分离、重大事件复核 | 新旧情绪策略先并行计算，达到指标后按行为类型逐步启用 |
| `Humanoid Core` | 基线与短期变化分离、社交能量、夜间状态、Provider 回退 | 提供低成本本地更新和模型不可用时的稳定降级 |
| `Period` / `LivelyState` | 身体状态独立于情绪、主体归属、显式状态迁移 | 身体和环境只提交 `ObservationSignal`，由角色策略解释其情绪意义 |
| `ToT Memory` / `FavourPro` | 先计算关系和行为倾向，再翻译为语言；关系状态映射表达 | `MotiveState` 与 `ExpressionPosture` 独立生成，LLM 只负责最终表达 |

**状态分层**固定为四层，禁止用一个全局心情覆盖全部用户：

1. `AffectBaseline`：人格或生活阶段的慢变化基线，例如敏感度、恢复速度和默认社交需求。
2. `AffectState`：由近期事件投影出的短期状态，按“人格 + 用户 + 会话/窗口”隔离，带版本、来源和恢复阶段。
3. `RelationshipProjection`：针对特定用户或群作用域的信任、亲近、边界和修复需求；不能从一个用户复制到另一个用户。
4. `BodyContext`：睡眠、精力、天气、生理周期和环境等观测；它们是情绪解释的输入，不自动等同于某种情绪。

状态不直接保存模型生成的“心情故事”，而保存有界数值、标签、事件引用、置信度、有效期和修订关系。事件采用追加记录，状态采用带 `revision` 的快照；任何投影失败都不覆盖上一份有效状态。

**运行时路径**固定为：

```text
消息 / 记忆 / 日历 / 身体与环境观测 / 动作回执
                         |
              AffectEventProducer
          (本地规则先行，必要时低频 LLM 复核)
                         |
                 AffectEventLedger
                         |
              AffectStateProjector
       (阻尼、半衰期、基线、影响图谱、恢复)
                         |
     RelationshipProjection + BodyContext + CalendarContext
                         |
                  MotiveProjector
                         |
        ThoughtSeed / CandidateModifier / ExpressionPosture
                         |
                 Kernel 统一决策与投递
```

**模型调用策略**：

- 普通消息先做确定性的引用、去重和过期检查，复用已有语义结果；没有可靠解释时不强行更新情绪，不增加同步 LLM 调用。
- 按消息数量、话题结束、状态变化幅度或固定采样比例触发异步分析；分析任务可取消、可退避，有失败冷却。
- 争吵、道歉、关系修复、明显安全风险等重大事件即时复核，但仍由规则限制强度和有效期。
- LLM 只能输出事件类型、证据引用和置信度，不能直接写入情绪分数、人格、权限或发送请求。
- LLM 不可用时使用上一次有效投影和中性 `ExpressionPosture`，主对话不能被情绪分析阻塞。

**与角色扮演的连接**只开放三种结果：

- `ThoughtSeedContribution`：提高“关心、修复、分享、休息、探索”等候选的有限倾向；不能生成或发送消息。
- `CandidateModifier`：调整候选的时机适配、连续性价值、打扰成本和表达形式；不能改权限、硬上限和证据等级。
- `ExpressionPosture`：调整距离、温度、直接程度、长度、追问数量、语音节奏和媒体偏好；不能编造事实或承诺。

**明确排除的实现**：全局 `mood_score`、每条消息调用远程 LLM、固定阈值直接主动关心、随机不回复、显式输出 `<thought>`、情绪阶段锁死人格，以及“负面状态直接关闭所有主动行为”。这些最多作为可回滚的实验策略，不能成为 Kernel 默认行为。

**落地顺序**：

1. 定义 `AffectEvent`、`AffectState`、`RelationshipProjection`、`BodyContext` 和 `ExpressionPosture` 的 Schema 与作用域校验。
2. 建立影子事件账本和投影快照，接入旧情绪插件的只读事件；旧生产路径继续生效，新路径不写 prompt、不执行外部动作。
3. 先以 `observe` 模式运行新投影，比较状态跳变、误归因、恢复时间、模型调用量和主动抑制率。
4. 接入关系和身体观测适配器，验证用户隔离、有效期、撤回和模型故障降级。
5. 让情绪结果只影响候选排序和表达姿态，按低风险行为类型灰度启用；重大事件保持人工或策略复核入口。
6. 连续一个完整观测周期满足稳定性、资源和兼容门禁后，迁移状态并退役旧的独立情绪注入入口。

这条路线的原则是：情绪负责改变角色的“在意程度、恢复速度和接触成本”，关系负责说明“对谁”，动机负责说明“想做什么”，而 Kernel 负责决定“能否以及何时行动”。

3.10.1 定义领域语义，3.10.2 定义实现步骤，本节只记录选型依据；同一策略只有一个版本源。影子、切换与回退统一遵循 4.1，不在各情绪入口另设迁移状态机。

### 3.10.4 情绪系统验收指标

- **归因准确性**：转述第三方、用户自述和直接对 Bot 的话不会混淆；对象不明时保持低置信度。
- **状态稳定性**：普通消息不造成跳变；重大事件影响更强但有上限；衰减和恢复时间可解释。
- **动机有效性**：候选主题更丰富，但不会因为“有情绪”而强行发消息；允许稳定返回空结果。
- **行为边界**：情绪不能越权发送、控制设备、修改权限或覆盖用户频率设置。
- **表达一致性**：姿态能改变距离、长度、追问和 TTS 风格，但事实内容仍由主模型和工具结果决定。
- **性能和可恢复性**：普通对话不增加同步 LLM 调用；辅助分析可取消、可退避；插件重载后无旧任务回写。
- **可审计性**：每次状态变化都能回到事件、策略版本、动机投影、候选和最终回执，且诊断数据不含原始隐私内容。

### 3.11 自检、诊断和答疑

自检和答疑不能以“从说明书找到一段最像的文字”为主要实现。说明书只能解释设计意图；故障结论必须来自当前配置、运行状态、事件轨迹或一次实际检查。

诊断分为四种模式：

| 模式 | 作用 | 是否执行检查 |
| --- | --- | --- |
| explain | 解释功能、调用链、配置和设计取舍 | 否 |
| self_check | 检查依赖、配置、能力、任务和资源状态 | 只读检查 |
| incident | 根据作用域和时间窗口重建一次具体故障 | 只读检查，可读取审计轨迹 |
| repair_proposal | 给出可执行修复候选和影响范围 | 不直接修改，需确认 |

统一链路为：

~~~text
用户问题
  -> 识别诊断模式、作用域和时间窗口
  -> 收集相关 Check/Probe 的结构化证据
  -> 构造候选假设并标注支持/反对证据
  -> 计算结论置信度和未决项
  -> 模型组织自然语言答复
  -> 可选生成待确认修复建议
~~~

外部插件可以注册 DiagnosticCheck，但只能声明检查范围、成本、权限和副作用。检查结果必须返回 pass、warn、fail、unknown 或 not_applicable，并携带检查版本、耗时、证据引用和脱敏详情。检查不得默认启动永久轮询，也不得在答疑过程中偷偷修改配置或设备状态。

首批标准检查类型包括：

- 合同和配置：配置项类型、范围、迁移状态和互斥关系；
- 能力和依赖：扩展版本、能力协商、权限和外部 Provider；
- 生命周期：插件实例、任务、连接、取消和热重载状态；
- 数据和日历：作用域、时区、事实来源、投影和最近写入；
- 消息投递：目标解析、平台能力、发送回执和重复发送；
- 资源和性能：任务并发、缓存大小、最近耗时、超时和退避；
- 事件轨迹：指定会话在时间窗口内的输入、候选、拦截、动作和回执。

诊断报告应至少包含：

~~~text
结论：当前最可能的原因和影响范围
依据：实际检查、配置、事件或回执
不确定性：缺失证据、冲突证据和检查时间
下一步：用户可执行的观察或检查
修复建议：变更项、前置条件、风险和回滚方式
~~~

模型只能在报告证据中存在对应检查结果时声称“已检查”“已发送”或“已修改”。没有执行证据时，必须使用“从配置/代码看”“目前无法确认”等表达。说明书内容可以帮助解释结果，但不能替代结果。

诊断能力本身属于主插件控制面：扩展管理页应显示检查名称、版本、最近状态、耗时、权限、资源成本和最近错误；答疑命令只读取经过作用域过滤和脱敏的报告。高成本检查按需执行并使用短期缓存，避免每次答疑都重复扫描源码、网络或设备。

诊断执行采用四级升级策略，以效率和证据强度共同决定是否继续：

| 等级 | 数据来源 | 默认行为 |
| --- | --- | --- |
| L0 | manifest、配置 Schema、静态依赖和能力状态 | 每次答疑可执行，目标是毫秒级 |
| L1 | 当前任务、缓存、最近错误、投递回执和本地状态 | 与 L0 并行执行，短期缓存 |
| L2 | 指定 Scope 和时间窗口的事件/审计时间线 | 只有问题涉及具体事件时执行 |
| L3 | 网络、设备、Provider 或可复现探测 | 证据不足且用户授权时执行，必须有超时和取消 |

诊断报告中的每个 Finding 都必须关联支持证据，并记录已找到的反对证据；没有反对证据时列表可为空，不能制造证据凑齐字段。首期使用有理由的 `low/medium/high/unknown` 证据等级，未经过标注样本校准前不声称是故障概率。数值置信度若保留兼容字段，需说明评分版本与含义；模型不能自行提高等级。检查无法执行时使用 unknown，不得当作 pass。

结构化诊断报告保留“结论、依据、不确定性、下一步、修复建议”字段，用户答复按问题只呈现必要部分，不强制每次展示五段模板。说明书、源码摘录和关键词索引用于解释静态判断，不能替代实际运行证据。

### 3.12 主动消息构建

主动系统的核心单位不是“主动消息”，而是 InteractionOpportunity（主动接触机会）。一次机会可以被合并到当前回复、延后、取消、保持沉默，或最终产生文字、媒体、动作和持续会话。消息只是机会被接受后的一个结果。

#### 3.12.1 主动来源和信号模型

主动来源只负责报告“发生了什么”或“当前观察到什么”，不能直接创建面向用户的消息。所有来源先将数据转换为统一的 `Signal`，再交给主动候选生成器。

来源按职责分为：

| 来源 | 作用 | 例子 |
| --- | --- | --- |
| calendar | 提供现实承诺、时间段和截止点 | 会议临近、活动结束、安静时间开始 |
| life_state | 提供角色或用户的状态变化 | 睡眠不足、精力下降、情绪变化 |
| user_interaction | 提供对话和用户行为变化 | 用户重新出现、长时间未回应、话题结束 |
| external_observation | 提供设备、位置、天气和健康观测 | 到家、运动结束、暴雨预警 |
| memory_relationship | 提供共同经历和关系连续性线索 | 未完成话题、纪念日、关系修复节点 |
| goal_project | 提供长期目标的进度和机会 | 创作进度、旅行准备、学习截止点 |
| extension_content | 提供外部扩展产生的内容事件 | 直播、游戏、新闻、作品更新 |
| persona_internal | 提供 Bot 内部模拟生活状态 | 自己完成一段活动、产生待分享想法 |
| system_lifecycle | 提供系统运行事件 | 任务完成、服务恢复、能力失效 |
| user_directive | 提供用户明确安排的主动行为 | 稍后提醒、定期汇总、停止某类通知 |

来源分为 `push`、`pull` 和 `derived` 三种模式。`push` 在事件发生时上报；`pull` 按需或按窗口读取当前状态；`derived` 由 Kernel 根据已有信号计算，不得冒充原始观测。主动系统不应为每个来源各自启动永久轮询。

统一 `Signal` 至少包含：

~~~text
signal_id
signal_type
source_id
scope
occurred_at
observed_at
valid_from
valid_until
payload 或 resource_ref
evidence
confidence
sensitivity
dedupe_key
revision
trace_id
~~~

`occurred_at` 表示事情发生的时间，`observed_at` 表示系统看到它的时间；两者不能混用。`valid_until` 到期后信号只能用于历史诊断，不能继续产生新的主动机会。原始健康数据、精确坐标和媒体使用 `resource_ref` 或经过语义化的摘要，不直接复制到主动队列。

信号进入 Kernel 后依次进行格式校验、作用域校验、权限过滤、去重、时效判断和标准化。只有标准化成功的信号才允许触发候选；信号本身不代表需要联系用户，也不代表事实已经得到用户确认。

每个来源通过 `SignalSourceDescriptor` 声明信号类型、推送/拉取模式、最低证据、新鲜度、权限、可靠性、最大频率、资源成本和失败策略。来源失效、数据过期或权限撤销时，Kernel 将其标记为 `unknown`/`unavailable`，不会把旧信号继续当作当前事实。

同一信号可以被多个主动类型消费，但候选生成必须携带 `signal_id` 和 `evidence_refs`。这样可以追溯“哪一个天气观测产生了哪一次提醒”，也能在用户新消息到达后取消尚未投递的相关机会。

主动消息采用“统一调度骨架 + 类型独立策略”。每种主动类型可以保留自己的触发解释、证据要求、内容意图和回退方式，但候选生命周期、权限、日历约束、资源预算、去重、投递和审计由 Kernel 统一负责。

#### 3.12.2 信号稀疏与饱和型候选

陪伴型 Bot 不能假设“外部信号足够多”。天气、日历、设备和用户消息属于重要输入，但在长时间没有外部变化时，Bot 仍需要维持角色生活、关系连续性和适度的主动可能。因此主动系统必须区分“信号供给”和“候选供给”：

~~~text
信号：少量、可信、可追溯的事实/状态/机会
候选：针对同一信号生成的多个可比较行为方案
机会：经过用户策略和当前情境筛选后的一次实际接触
~~~

一个信号不应只绑定一条待发送消息。例如“用户结束工作并进入空闲状态”可以扩展为问候、延续未完成话题、分享 Bot 的内部活动、邀请共同活动、等待下次对话合并提及或保持静默等候选。候选是行为方案，不是六条消息；同一 `CandidateSet` 中最后最多产生一个接触机会。

候选扩展的标准流程为：

~~~text
Signal / ThoughtSeed
  -> Candidate Expansion
  -> CandidateSet 归一化、去重和语义聚类
  -> 用户策略、频率、日历、权限和资源检查
  -> OpportunityArbiter 竞争
  -> IntentPlan
  -> 消息、媒体、动作、持续会话或静默
~~~

候选可以从三种来源共同产生：

| 来源 | 作用 | 约束 |
| --- | --- | --- |
| rule | 生成稳定、低成本的基础方案 | 只能使用已知事实和类型策略 |
| extension | 提供领域特有的意图或动作方案 | 不得直接发送、伪造紧急程度或修改用户策略 |
| model | 在已通过准入的信号上补充目的、时机和形式的变化 | 不能增加事实、证据、优先级或权限 |

模型的职责是扩大少量已准入信号的行为选择，不是每个调度 tick 自由制造念头。内部生活、关系连续性和空闲窗口可以产生 `ThoughtSeed`，再进入候选扩展；没有合适主题时返回空结果，静默是有效结果。

候选饱和度和实际接触频率必须分开控制：

~~~text
候选预算：一次决策允许比较多少方案
接触预算：用户在时间窗口内最多收到多少主动行为
~~~

低频用户也可以拥有多个候选供调度器选择，但最终只发送极少的消息。候选默认先以内存中的 `CandidateProposal` 存在，只有通过准入并可能跨调度轮次存活的方案才转为持久化 `ActiveCandidate`；没有胜出的方案不进入延后队列。

每个 `CandidateSet` 必须有边界：

- 限制单个信号的最大候选数 `max_candidates`；
- 按用户、来源、主动类型和时间段限制候选计算预算；
- 使用 `semantic_key`、`merge_group` 和 `supersedes_key` 合并同主题方案；
- 为候选方案设置短期 `proposal_ttl`，避免未胜出方案长期占用内存；
- 只有一个方案可以成为当前车道的 `InteractionOpportunity`，其余方案转为合并、保留、抑制或过期；
- 队列拥塞时向来源返回反压结果，要求降低采样或停止产生候选。

候选扩展可以沿四个维度产生差异：行为目的（关心、分享、提醒、邀请、帮助、行动、持续会话）、接触时间（立即、当前回复合并、时间窗口、下次聊天、摘要、放弃）、表达形式（短句、问题、媒体、建议、投票、动作）和关系意图（轻量陪伴、认真关心、角色连续性、共同活动、情绪支持）。这些维度只能在证据允许的范围内变化，不能为了“饱和”强行制造没有依据的行为。

候选评分仍由 `PolicyArbiter` 统一完成，至少考虑价值、时机匹配、关系连续性、新颖性、预期回应、延迟损失、打断成本、近期接触负担和冲突成本。候选生成阶段追求较高召回，机会选择阶段追求低打扰；两者不能合并成“产生即发送”。

#### 3.12.2.1 情绪与关系对主动行为的调制

情绪对主动行为的作用是“改变候选的倾向和表达成本”，不是“产生一条消息并立即发送”。主动系统采用以下边界：

```text
AffectState + RelationshipProjection + BodyContext + CalendarContext
                              |
                         MotiveState
                              |
             ThoughtSeed / CandidateModifier / ExpressionPosture
                              |
              CandidateSet -> PolicyArbiter -> ContactBudget
                              |
                         IntentPlan / 静默
```

**一是影响想不想做什么。** `MotiveProjector` 将状态转换为有限的动机，再由候选生成器提出行为方案。例如：

| 状态或动机 | 可以增加的候选倾向 | 不允许的推断 |
| --- | --- | --- |
| `care`、`check_in` | 询问近况、提供帮助、把相关事件合并到下一次对话 | 不能假定用户一定需要安慰 |
| `repair_need` | 道歉、澄清、延续未完成话题 | 不能把沉默解释成用户生气 |
| `share_drive`、`connect` | 分享角色当下活动、邀请共同活动 | 不能虚构角色实际经历 |
| `rest`、高负荷、低社交能量 | 延后环境性分享、缩短内容、等待自然互动 | 不能因此永久关闭主动 |
| `boundary`、高脆弱度 | 减少追问、选择低侵入表达、必要时进入安全姿态 | 不能用情绪绕过安全和权限规则 |

**二是影响候选如何竞争。** `CandidateModifier` 只能调整 `readiness`、连续性价值、建议时间窗、打扰成本、追问倾向和形式偏好。它不能修改证据等级、主动类型的硬优先级、用户的频率上限、权限或投递状态。一个候选因情绪获得的加分必须有上限和 TTL，状态恢复后自动失效。

**三是影响接触形式，而非强行增加次数。** `ExpressionPosture` 将情绪和关系翻译为短消息、问题、媒体、建议、邀请、动作或静默等形式。高关心不等于多发消息，低能量也不等于消失；调度器应优先把内容合并到用户下一次自然对话，或选择更短、更低打扰的方案。

**四是用户预算拥有最终控制权。** 主动决策按以下顺序执行：

1. 权限、隐私、安全、事实有效期和日历安静时段等硬门槛；
2. 主动类型自身的时效和承诺规则；
3. 用户设置的 `ContactBudget`，包括每日范围、最小间隔、允许类型和未回应减速；
4. 情绪、关系和新颖性带来的软评分；
5. 生成表达和投递形式。

情绪不能突破用户预算。只有用户明确授权的高时效预警、现实承诺或安全事件，才可以按照对应的高优先级策略处理；普通的“想念”“担心”或“兴奋”只能提高候选竞争力，不能直接抢占发送车道。

**五是主动结果反向形成事件。** 用户回复、主动吸收、取消、忽略、平台回执和候选过期都写入 `InteractionLedger`，再由 `AffectEventProducer` 生成带来源和作用域的反馈事件。未回应只降低相关来源或同类候选的近期 readiness，不自动解释为拒绝、惩罚或关系破裂；重复失败、权限撤销和明确拒绝才可以触发更强的抑制或冷却。

这样，情绪系统可以让主动行为更像角色的自然念头：在意时更容易想到关心或分享，疲惫时更愿意等待，关系紧张时优先修复，但每一次实际接触仍由日历、权限、用户预算和统一调度器共同决定。

#### 3.12.2.2 动机层：从“在意”到“想做什么”

`MotiveState` 是主动系统的中间决策状态。它不是情绪标签、日程任务或待发送消息，而是一个面向目标的短期倾向。为了避免把不同层次的东西混成一组分数，动机采用四层模型：

```text
NeedSignal       身体、情绪或关系产生的驱动力
Goal/Commitment  用户或角色需要推进的目标、承诺或任务
MotiveState      在当前条件下选择推进的方向
Candidate        可以执行的具体行为方案
```

例如“用户最近状态低落”只是 `NeedSignal`；“维持关系连续性”是目标；`care` 是当前动机；“询问近况、提供帮助、等待下次对话合并”才是候选。这样情绪不会直接变成消息，日历承诺也不会被误当成心情。

**动机类别**按语义族固定，具体类型可以由扩展注册：

| 语义族 | 示例 | 说明 |
| --- | --- | --- |
| `maintenance` | `rest`、恢复精力、维持日常 | 多数是内部调节，也可以抑制低价值主动 |
| `relationship` | `care`、`repair`、`connect` | 面向特定用户或群作用域的关系方向 |
| `goal` | 学习、创作、旅行准备、未完成承诺 | 可由日历、用户指令或目标插件产生 |
| `response` | `assist`、`follow_up`、继续当前话题 | 对已有请求、事件或对话的回应意图 |
| `expression` | `share`、`explore`、角色生活分享 | 低承诺的自我表达和环境性陪伴 |
| `constraint` | `boundary`、安全、过载 | 限制或改变行为方式，不是普通消息候选 |

动机必须区分 `commitment_level`：`impulse`（一闪而过）、`preference`（偏好）、`commitment`（需要持续推进）和 `obligation`（用户明确要求或现实承诺）。只有后两者可以在多次评估中保留较长时间；普通分享和随机陪伴允许自然消失。

动机至少包含以下字段：

```text
motive_id / scope / kind / target_scope / beneficiary
drive / urgency / persistence / feasibility / intrusion_cost
commitment_level / conflict_set / evidence_refs / provider_refs
created_at / next_evaluate_at / valid_until / max_deferrals
satisfied_by / source_state_revision / status
```

动机由多个输入共同投影，而不是由情绪单独决定：

| 输入 | 对动机的影响 |
| --- | --- |
| `AffectState` | 改变在意程度、恢复速度和接触成本，例如提高 `care` 或 `repair` 的 drive |
| `RelationshipProjection` | 决定动机针对谁、关系连续性价值和边界强度 |
| `CalendarContext` / `Goal` | 提供时间窗口、截止点、承诺等级和可执行机会 |
| `BodyContext` | 限制精力、注意力、行动成本和可打断程度 |
| `InteractionLedger` | 根据回应、忽略、取消和已完成行动调整持续性与冷却 |
| 外部插件 | 提交带证据的 `MotiveContribution` 或机会信号，不得直接写入最终动机或发送请求 |

动机投影使用本地规则完成基础计算，必要时由 LLM 解释证据。LLM 只能提出动机类别、目标、置信度和建议强度；Kernel 负责校验作用域、权限、时效、承诺等级和上下限。情绪插件可以提出“值得关心”或“需要修复”的贡献，但不能提出“现在立刻发消息”。

**动机竞争**先处理硬约束，再进行软排序：

```text
作用域/权限/安全/事实有效性
        -> 现实承诺与用户明确请求
        -> drive + urgency + continuity_value
        -> feasibility - intrusion_cost - conflict_cost
        -> 公平性、老化和近期接触负担
        -> 当前候选方向或静默
```

多个动机可以同时存在，但每个作用域只保留有限的活跃集合（默认每类 1--2 个、总量 3--5 个，可配置）。`MotiveArbiter` 必须记录落选原因，并使用类别配额、老化加分和替换规则避免某一类动机长期挤占其他动机。动机冲突时不直接删除较弱动机：例如“想关心用户”与“精力不足”并存，可以选择延后、合并到下一次回复或发送一句短消息；“想继续聊天”与会议冲突时，日历限制可执行性，但不会删除关系动机。

动机有独立生命周期：

```text
latent -> active -> competing -> candidate_linked
       -> satisfied / deferred / suppressed / expired
```

`deferred` 只保存动机摘要、下次评估时间、延后次数和原因，不复制一条消息反复排队。`satisfied_by` 定义满足条件，例如用户已经回复、承诺事项已完成或动作收到成功回执。普通动机达到延后上限或失效时释放候选；用户承诺和 obligation 仍保存在权威任务/日历中，标记未完成及原因，不能因候选预算耗尽而消失。

外部插件通过 `MotiveContribution` 提交建议，最小字段如下：

```text
contribution_id / provider_id / scope / kind / target_scope
drive_delta / confidence / evidence_refs / valid_until
dedupe_key / supersedes_key / resource_cost / trace_id
```

贡献只影响动机投影的有限增量，不能覆盖基线、承诺等级、用户预算、权限或投递状态。来源失效、过期或撤销时，贡献自动退出；没有有效贡献时，Kernel 仍可根据已有目标和生活状态产生低成本动机。

动机到主动行为保持一对多映射：

| 动机 | 可生成的候选 | 可采用的处理形式 |
| --- | --- | --- |
| `care` | 询问、帮助、提醒用户休息 | 立即、时间窗口、合并到回复 |
| `repair` | 道歉、澄清、恢复未完成话题 | 当前对话优先，必要时短期跟进 |
| `connect` / `share` | 分享角色活动、邀请共同活动 | 普通或环境车道，允许静默 |
| `assist` / `follow_up` | 查询资料、执行已授权动作、跟进请求 | 先确认权限和可执行性 |
| `rest` / 过载 | 延后低价值主动、减少追问、缩短表达 | 静默或低负担短消息 |
| `boundary` / 安全 | 拒绝越界、停止追问、进入安全姿态 | 高优先级表达约束，不产生普通主动 |

动机只负责“为什么以及想做哪一类事”，时间由日历和机会窗口决定，次数由 `ContactBudget` 决定，形式由候选计划结合 `ExpressionPosture` 选择，执行由 `DeliveryGateway` 决定。`ExpressionPosture` 提供表达偏好，不单独决定动作或发送。`MotiveArbiter` 只筛选方向，`PolicyArbiter` 是机会准入与排序的唯一责任点；其他 scorer/modifier 不各维护队列或重复扣预算。

统一流程为：

~~~text
信号接入
  -> ThoughtSeed（可选）
  -> CandidateSet 饱和扩展
  -> 候选准入和归一化
  -> 作用域、权限和时间段检查
  -> 合并、去重、延后或抢占
  -> 判断是否值得打扰
  -> 生成 IntentPlan
  -> 生成文字/媒体/动作
  -> 投递并等待回执
  -> 记录经历、冷却和后续事件
~~~

信号先进入 OpportunityAggregator，再进入 PolicyArbiter。聚合器按 Scope、语义主题、时间窗口和 merge_group 合并不同插件产生的候选，并维护 parent_opportunity、thread_id、expires_at 和 dedupe_key。它必须允许沉默、合并、延后、抑制和过期，并记录对应原因。

PolicyArbiter 先执行过期、权限、安静时段、平台能力、预算和冲突等硬门槛，再根据相关性、新颖性、连续性价值、延迟损失、打断成本和近期接触负担进行软判断。没有合适机会时，沉默是成功结果，不应为了完成主动额度而发送低价值消息。

主动类型通过 ProactiveTypeDescriptor 注册以下策略：

| 字段 | 作用 |
| --- | --- |
| trigger_kind | 时间段、事件、状态变化或周期信号 |
| evidence_requirements | 触发所需的证据类型和最低新鲜度 |
| urgency | alert、normal 或 ambient |
| expires_after | 候选有效期 |
| interrupt_policy | 是否允许打断当前活动，以及在 `turn_open`/`engaged_thread` 时合并、延后或按授权抢占 |
| merge_group | 可与哪些候选或当前回复合并 |
| cooldown_policy | 最小间隔、重复判断和恢复条件 |
| generation_policy | 角色表达、事实短报、摘要或动作计划 |
| fallback_policy | 模型不可用时的安全回退 |
| resource_budget | 模型、网络、媒体和发送成本 |
| value_class | alert、commitment、care、continuity、ambient、invitation、share 或 digest |
| expected_response | 是否期待用户立即回答 |
| evidence_quality | 触发证据的可靠性和最低新鲜度 |
| max_event_rate | 提供方允许产生信号的速率 |

调度器使用三条优先级车道：alert 处理高时效预警和安全事件；normal 处理生活事件、目标进度和关系触达；ambient 处理早安、分享和轻量陪伴。高车道可以在授权范围内抢占低车道；低价值候选必须允许沉默、合并或过期，不能为了完成主动额度而硬发消息。

早安、晚安等周期候选应受起床/入睡窗口、近期自然互动和安静时段抑制；天气预警应支持来源可信度、生效/失效、更新和撤回；到家事件应要求位置授权、模糊区域、到达置信度和去抖；外部内容应支持相关性、新鲜度、已分享记录和批量摘要。它们共享调度骨架，不共享一套提示词或触发实现。

候选不能直接生成正文。模型先接收 IntentPlan，其中包含 purpose、emotional_stance、conversation_load、continuity_anchor、evidence_refs、forbidden_claims 和 preferred_modality。模型只能解释事实和意图，不能改变证据等级、主动优先级或投递状态。

主动机会通过 InteractionLedger 记录最近自然互动、主动联系、用户回应、候选取消原因、接触负担和已被当前对话吸收的事件。用户新消息应优先合并或取消同主题主动机会；连续互动形成同一 thread，不得拆成互相独立的通知。

机会生命周期为 created、eligible、merged/deferred/suppressed/expired、approved、generating、delivery_pending，实际发送结果由独立的 DeliveryReceipt 记录。平台受理与用户送达分开，未知结果和分段部分成功按 3.12.4 对账，不重新生成整条消息。用户新消息优先吸收同主题候选，不取消无关的明确提醒；候选过期、授权撤销或绑定失效时取消尚未开始的投递，已开始的部分保留真实回执。

配置主要控制主动模式、每日预算、最小间隔、安静时段、允许的候选类别、可打断活动和外部动作权限。具体发送时刻由日历时间段、用户状态、候选价值和近期互动共同决定，不由每个类型自行维护永久定时器。

#### 3.12.2.3 对话连续性与插话闸门

“当前有空”与“现在适合插话”是两个不同的判断。每次主动机会在生成、批准和提交前都读取同一份 `ConversationOccupancy`；机会不能因为来源是 `persona_internal`、已经生成了图片，或命中了可用时间窗口，就跳过对话闸门。主动决策顺序固定为：

~~~text
读取 ConversationOccupancy
  -> 绑定 active_thread_id / topic_fingerprint
  -> 吸收同主题候选，标记无关候选 defer/suppress
  -> 判断 interrupt_policy、媒体打扰成本和时效
  -> 生成或取消资源任务
  -> 生成 IntentPlan / 当前回复
  -> 以 conversation_revision 再校验
  -> 统一投递并记录回执
~~~

候选与对话阶段的默认矩阵如下；用户明确请求、已授权的现实承诺和安全事件仍按各自证据与权限规则处理：

| 当前状态 | 可以进入当前回复 | 默认动作 | 允许抢占的例外 |
| --- | --- | --- | --- |
| `turn_open` | 当前用户问题、同主题事实、用户请求的媒体 | 合并到本轮；无关候选不生成正文，已生成但未提交的媒体取消或保留引用 | 已授权的 `alert`/安全事件，用简短可恢复的表达 |
| `engaged_thread` | 当前主题的跟进、用户刚询问的内容、与线程目标直接相关的提醒 | 吸收同主题；无关 `share`、`ambient`、邀请和角色生活更新延后到 `closing`/`idle`，不单独发图。明确预约的提醒保留待处理状态，按其时效策略排队 | 具有明确时效和授权的提醒，排在本轮之后；安全事件按策略处理 |
| `closing` | 收尾所需的摘要、确认和相关分享 | 低负担合并或等待空闲宽限结束；不重新打开已收束话题 | 到期的高时效承诺或安全事件 |
| `idle` | 经准入的主动机会 | 按车道、日历和预算投递 | 由 `authorized_preempt` 明确声明并通过权限校验 |
| `quiet` | 用户主动发起的请求 | 普通候选抑制；直接请求仍响应 | 仅授权安全/现实承诺流程 |

`ProactiveTypeDescriptor.interrupt_policy` 由简单布尔值扩展为可解释的 `never_during_turn`、`defer_when_engaged` 或 `authorized_preempt`；旧布尔值迁移为 `false -> defer_when_engaged`、`true -> 仍需声明可抢占证据和权限`，不能把 `true` 当作无条件插话许可。`value_class=ambient|continuity|invitation|share` 的默认策略是 `defer_when_engaged`，事务/安全类型必须另行声明时效、证据和抢占理由。

媒体是高打扰成本的表达形式。`preferred_modality=media` 只表达偏好，不能改变闸门；在 `turn_open` 或 `engaged_thread` 中，媒体必须满足以下任一条件才可进入当前回复：用户明确要求、媒体直接回答当前问题、或候选与当前 `topic_fingerprint` 具有可解释的同主题关系。角色内部刚完成吃饭、散步、拍照等活动不构成发送理由。图片生成应在机会获准后再启动；若生成期间对话 revision 进入与原机会不兼容的 `turn_open`/`engaged_thread`，未提交的 `MediaJob` 转为取消、延后或仅保留短期资源引用，不能悄悄补发；同主题且由用户请求的媒体可以继续随当前回复完成。

PromptCompiler 必须把以下字段传给表达模型：`conversation_phase`、`conversation_load`、`active_thread_id`、`topic_fingerprint`、`continuity_anchor`、`pending_opportunity_summary` 和 `defer_rules`。提示词约束至少包括：“先完整回应当前话题；不要在回复中夹带未请求、与当前主题无关的角色生活更新或图片；可分享念头记录为延后候选；只有当前话题需要、用户询问或已通过机会闸门时才使用媒体。”模型可以改写语气和合并方式，但不能把延后候选改成已获准投递，也不能改变 `interrupt_policy`、权限、证据等级或预算。

`ResponsePlan`/`DeliveryPlan` 应回传 `absorbed_opportunity_ids`、`deferred_opportunity_ids`、`conversation_revision` 和 `delivery_owner`。提交前若 revision 变化，重新执行占用态和权限检查；未提交的计划进入 `deferred(conversation_busy)` 或 `superseded_by_thread`，已提交的动作只进入真实回执对账，不能假装取消。InteractionLedger 记录 `absorbed`、`deferred`、`suppressed`、`interrupted` 及原因，并单独统计无关媒体打断率、同主题吸收率、延后后自然合并率和高时效事件延迟，作为策略调参依据。

~~~text
用户发来散步中的连续消息
  -> ConversationOccupancy = engaged_thread
  -> 娃的吃饭 ActivityEpisode 只进入 persona_internal
  -> share 图片候选标记 defer(conversation_busy)
  -> 当前回复完成，候选再次评估
  -> 若话题已收束则合并/延后；若用户问“吃饭了吗”才作为同主题媒体回复
~~~

这一闸门解决的是“事件发生就发消息”的旁路问题，同时保留自然生活模拟：角色可以继续拥有吃饭等内部活动，系统也可以保存待分享念头，但主动接触必须等待当前关系线程给出合适的出口。

#### 3.12.2.4 对话收束是状态信号，不是词条门禁

最近一次回归暴露了一个具体断链：Bot 在 23:56 发出晚安后，00:31 又由普通 `open_loop` 候选重新开了一个话题。现有休息闸门只解析用户入站文本，Bot 的晚安只是可见文本，没有进入对话占用态；因此 `last_proactive_reason=check_in`、`source=open_loop` 的候选仍被视为可以发送。这个案例说明，拟人性问题不是缺少“晚安”关键词，而是发送意图没有形成可供后续候选读取的短期关系状态。

重置后的规则应把主动消息的对话姿态作为候选协议字段，至少区分 `closing`、`open` 和未声明三种状态。姿态由来源适配器或 `IntentPlan` 产生，不从正文反向猜测，也不依赖某种语言的词条。晚安、结束陪伴、暂时收住等语义候选可以声明 `closing`；普通分享、提醒和用户明确触发的跟进不应因为正文里出现相似词语而自动变成收束。

`closing` 发送成功后，只写入会话级的短期状态，例如 `conversation_closing={at, until, posture, source, reason}`。它与 `UserRestGate`、日历和人格生活事实分开，默认采用可配置的短暂宽限（当前兼容实现使用 `proactive_closing_grace_minutes`），到期自动失效。用户出现新的入站活动时，按活动时间戳使该状态失效；不需要再写一套“醒了/可以聊”的关键词取消规则。

候选处理采用软延后而不是硬拦截：在收束窗口内，普通、无触发、非时效候选整体顺延并保留原始来源、主题、触发和有效期；明确用户请求、现实承诺、定时器和安全/高时效事件仍按自身车道处理。顺延必须可重入、可合并、可过期，不能复制一条新的候选来“补发”。候选重新进入窗口时再次读取收束状态，避免生成时通过、提交时越过状态变化。

表达模型应收到同一份收束上下文，但只把它当成写法和节奏约束：普通候选不要借机重新开话题；本轮已有明确新来源、用户新消息或高时效事项时才自然承接；正文不能解释内部状态。模型可以把候选改成更短的句子，但不能把被延后的机会改成已获准投递，也不能把收束状态解释成用户已经睡着。

验收至少包含以下回归：

| 场景 | 预期 |
| --- | --- |
| Bot 发送带 `closing` 姿态的晚安后，普通 `open_loop` 到达 | 候选保留并顺延到宽限结束，不在晚安后立即另起话题 |
| 收束窗口内用户发来新消息 | 旧收束失效，相关主题候选可以合并到当前线程 |
| 收束窗口内出现明确提醒、定时器或安全事件 | 依据车道和时效继续评估，不被普通留白状态吞掉 |
| 晚安正文改成别的语言或没有固定词 | 仍由语义姿态生效，不能靠关键词命中与否决定行为 |
| 候选在生成后、提交前发生用户活动或收束到期 | 以最新会话 revision/状态重新判断，不能沿用旧的“可发送”结论 |

当前实现可以把姿态和收束状态落在兼容字段中，但新架构应把它们迁移到 `ConversationOccupancy` 与 `InteractionLedger`：前者负责当前会话阶段和 revision，后者记录 `deferred`、`absorbed`、`expired` 及原因。这样才能把“说完晚安后留白”作为可解释的关系节奏，而不是散落在发送函数里的中文正则或永久沉默开关。

#### 3.12.2.5 未回应计数必须属于用户持久状态

未回应次数是跨调度轮次的用户互动状态，不能只放在心跳对象、临时 `runtime_state` 或进程内变量中。兼容实现以用户记录的 `unanswered_proactive_count` 为主字段，读取旧版 `ignored_streak` 并在加载时迁移；主动消息成功且声明等待回复时递增，用户出现新入站活动时清零，两个字段在迁移期保持镜像。发送结算和入站清零都在同一份用户记录保存边界内完成，重启、重载和切换调度器不会重新把次数当成 0。

“达到几次后暂停”属于策略配置，不应写成 `if count >= 3` 一类的业务常量。`proactive_unanswered_pause_after` 默认 0，表示只按未回应策略降频；设置为正数时才暂停普通主动，定时器等明确车道仍由各自规则处理。暂停状态不删除计数，用户下一条消息负责恢复并清零。测试至少覆盖旧字段迁移、重启后的持久读取、连续递增、入站清零和阈值关闭/开启两条路径。

### 3.12.3 现有策略资产继承与迁移

现有主动系统已经经过多轮真实使用和回归修正。综合评分、来源优先级、语义判断、人格匹配、去重、冷却、未回应减速、专项事件判断和投递失败处理，都属于需要保留的策略资产。重置的对象是职责边界和数据流，不是把这些结果重新猜一遍。

策略资产的判断标准是“它是否解决过一个真实问题，并且有代码、配置或测试可以证明”。单个常量不自动视为经验；只有当它的适用范围、影响结果和失败处理可以解释时，才迁移为新策略。历史实现中互相覆盖的同类规则应合并为一个有名称、有版本的策略，保留原有行为作为迁移基线。

#### 资产清单

| 现有策略资产 | 已验证的行为结果 | 新架构归属 | 迁移要求 |
| --- | --- | --- | --- |
| 综合评分 | `salience`、`urgency`、`warmth`、路线偏置、来源反馈、时间衰减、人格和语义分数共同决定候选竞争力 | `OpportunityScorer` | 拆成可解释特征；保留默认权重、边界和策略版本 |
| 语义判断 | 识别主动类型、语义锚点、触发证据、打扰压力、风险和关系越界 | `CandidateEligibility` | 明确证据等级；质量问题优先软降权或提示词约束，事实/安全风险才阻断 |
| 人格匹配 | owner/friend 差异、亲密表达、语音/图片/观察动作匹配、世界观边界 | `PersonaPolicy` | 与通用评分解耦；输出分数、说明和 blocker |
| 路由策略 | 事务、安全事件、延续、仪式、内容分享、自生活、关系互动拥有不同的重试、取消、回应预期和去重规则 | `BehaviorTypeDescriptor` | 保留类型独立策略；统一生命周期和投递接口 |
| 来源优先级 | 定时器、天气、健康、提醒、环境变化、跟进、日常问候、随机等有不同优先级 | `PriorityArbiter` | 转换为时效等级、价值等级和可抢占车道，避免散落的来源常量 |
| 去重与合并 | 稳定事件 ID、主题指纹、时间窗合并、高优先级替换低优先级 | `OpportunityAggregator` | 统一 `dedupe_key`、`merge_group`、`supersedes_key`，记录合并原因 |
| 频率和用户差异 | 每日额度、最小间隔、空闲时间、主动强度、群/私聊差异和未回应减速 | `ContactBudget` | 候选预算与接触预算分离；硬上限只作为最终保护 |
| 来源反馈 | 按来源统计发送、回复、正负反馈，且将学习影响限制在有界范围内 | `FeedbackLedger` | 不用全局沉默惩罚所有来源；设置最小样本量、衰减和上下界 |
| 时间与日历 | 活动曲线、能量、当前日程、重要日期、chronotype 和有效窗口影响主动时机 | `TimingPolicy` | 只读取统一的时间段视图；禁止各来源自行维护永久定时器 |
| 延后和失败治理 | TTL、最佳时间、指数退避、过期、`uncertain` 投递和回执查询 | `CandidateLifecycle` / `DeliveryManager` | 状态转换统一；重试必须使用幂等键，不重新生成重复消息 |
| 专项事件纠正 | 天气首次刷新建立基线；环境变化有通用冷却；目标进度必须有具体证据；习惯需要跨日证据 | 各领域 `SignalAdapter` | 保留领域规则和回归测试，不塞进通用评分器 |
| 外部能力管理 | 直播开播/下播、游戏邀请、边界转达等注册元数据、可用性、配置、冷却和执行器 | `CapabilityRegistry` | 扩展持有实现，Kernel 只负责准入、调度、授权、审计和回执 |

#### 规则分层

每条策略必须明确自己属于哪一层，禁止同一判断在多个阶段重复实现：

~~~text
事实与权限门槛       过期、作用域、用户授权、平台能力、安全事实不成立
候选准入             证据不足、重复主题、关系不合适、当前时间段不适合
候选评分             价值、时机、连续性、新颖性、延迟损失、打扰成本
表达约束             角色口吻、事实保真、禁止暴露内部机制、低压力表达
投递与回执           幂等、分段、媒体动作、失败、重试和最终状态
反馈更新             回应质量、忽略连续次数、来源表现和冷却调整
~~~

硬校验用于作用域、授权、明确免打扰、协议有效性、资源硬上限和重复动作防护。证据不足时优先降低断言强度、请求澄清或选择其他候选；需要真实完成证据的动作成功声明必须保留限制。平台缺少幂等支持时允许一次受控发送，但不能自动重试结果不确定的发送。空泛、语气过重、与人格不合等质量问题优先通过降权、提示词改写或更换形式解决；同一已执行动作的精确去重属于协议校验。

#### 策略资产格式

新系统使用 `PolicyAsset` 记录可迁移策略，而不是把规则继续埋在业务函数中。最小字段如下：

| 字段 | 含义 |
| --- | --- |
| `asset_id` / `version` | 稳定名称和可回滚版本 |
| `scope` | 全局、人格、用户、会话、来源或行为类型 |
| `inputs` | 使用的信号、候选字段、时间段和反馈字段 |
| `decision_kind` | `gate`、`score`、`merge`、`prompt`、`retry` 或 `settlement` |
| `parameters` | 默认权重、阈值、衰减、冷却和上下界 |
| `evidence` | 规则来源、回归案例、测试或观测指标 |
| `failure_policy` | `defer`、`merge`、`rewrite`、`cancel` 或 `drop` |
| `telemetry` | 命中次数、拒绝原因、发送结果、回复和资源成本 |

模型可以参与语义分类、候选扩展和表达改写，但不能修改 `PolicyAsset` 的权限、证据等级、优先级、预算或生命周期状态。来源反馈只能在满足最小样本量后对软评分产生有界影响，且必须记录使用的策略版本，便于解释“为什么这次被选中或被压低”。

#### 迁移步骤

1. **冻结行为基线**：保存现有配置、候选字段、状态转换、关键阈值和专项测试结果，先记录发送量、重复率、延后率、过期率、回复率、Token 消耗和资源占用。
2. **建立资产目录**：为每个规则补充适用来源、输入证据、决策层、失败处理、测试和观测指标；发现重复规则时以实际行为和测试结果为准合并。
3. **提取而不改值**：先把现有权重、冷却和优先级搬进 `PolicyRegistry`，保持策略版本 `legacy-compatible`，不在提取阶段同时重新调参。
4. **影子运行**：新策略只计算不投递，与旧结果并行比较候选排序、合并、延后和阻断原因，差异写入审计而不影响用户。
5. **按类型切换**：先切换事务、天气、目标和内容分享等边界清晰的类型，再切换关系、随机和外部动作；每次只启用一个策略版本。
6. **观测后校准**：根据同一指标窗口调整特征权重和提示词约束。任何阈值变化都必须注明原因、影响范围和回滚版本，稳定运行一个周期后才删除旧兼容路径。

迁移验收不以“发送更多消息”为目标，而以行为质量和资源稳定为目标：高时效事件不能丢失，低价值候选可以安静消失，同一事件不能重复触达，用户新消息能够吸收相关候选，未回应能够只影响相关来源，扩展失效不会阻塞主链，所有拒绝和降级都可解释。

### 3.12.4 投递、预算与副作用结算

DeliveryGateway 协调本体系接管的投递，Adapter 使用平台真实能力执行。它不保证端到端 exactly-once，也不能从 HTTP 成功推断用户已读。

| 状态 | 含义 | 历史与重试 |
| --- | --- | --- |
| pending | 尚未向平台提交 | 可在最终权限/版本校验后执行或取消 |
| submitted | 已发出请求，尚无明确受理结果 | 保留待对账记录，不声称成功 |
| accepted | 平台已确认受理，附平台 ID 或可核验的受理依据 | 可写入带状态的发送历史；不能表述为用户已读 |
| delivered | 平台提供明确送达回执 | 更新历史状态，不重复写一条消息 |
| partial | 分段消息或多模态中仅部分成功 | 逐部分结算，只处理未成功部分 |
| uncertain | 提交后超时、断线或回执丢失 | 优先按平台 ID/幂等键查询；不支持查询和幂等时保持未知，不自动重发 |
| failed / cancelled | 已确认未成功，或提交前取消 | 根据错误与有效期决定重试或结束 |

每个 DeliveryPlan 固定 `delivery_id`、目标、正文/资源摘要及有序 `part_id`；同一逻辑执行重试复用幂等键，新一次用户请求使用新键。进入执行前在本地事务中认领机会并预留 ContactBudget，防止并发候选超额；按已受理部分结算接触，确认未发送部分释放预留，未知部分保守记账并保留对账。额度按显式时区和窗口计算，未知状态不能在窗口内反复释放并重试。

平台发送与本地落账无法构成一个事务。发送意图先持久化，再执行，最后记录回执；重启扫描 submitted/uncertain 并对账。仅有本地幂等键不能证明平台支持幂等，SDK 需声明查询、幂等、撤回、分段和送达回执能力。

发送历史保存已受理的实际部分；uncertain 内容只能作为明确标记的待对账记录，不能混入模型的既成对话。长期记忆仍由 Memory Service 决定是否收录，发送成功不等于用户接受某项事实或承诺。媒体失败后只降级缺失部分，不重发已经成功的文本。

用户新消息、人格切换与卸载通过 revision/generation 校验阻止尚未提交的动作。取消请求不能撤销正在远端执行的动作，结果需进入对账或明确补偿流程。动作回执本身不授予下一次执行权限，同一因果链重放不得再次触发设备或付费动作。

#### 3.13.2 实现原则

1. **先契约，后功能。** 任何新扩展先实现 manifest、能力描述、作用域、事件和回执，再接入主链；没有契约的功能只能以兼容适配器存在。
2. **先观察，后生效。** 情绪、关系、主动排序和外部关心都先进入 `observe/shadow`，只生成预测、差异和审计，不直接触达用户。
3. **信号与行为分离。** 外部插件只报告事实或观察，候选生成器负责解释机会，Kernel 决定是否投递，执行插件只返回回执。
4. **复用 AstrBot 正式链路。** 主动调用优先构造标准 Agent 事件，经过人格、工具、分段、TTS 和发送后 hook；不能因为主动行为再造一条裸 LLM 链路。
5. **数据最小化。** 原始健康、位置、邮件和屏幕内容留在提供方；Kernel 只接收有作用域、有效期、证据引用和脱敏摘要的 DTO。
6. **所有状态都有出口。** 每个候选、任务、连接和动作都必须有取消、过期、失败、重试、卸载和不兼容路径；“没有结果”是可记录的正常结果。

#### 3.13.4 市场方案验证切片

首批切片只验证协议和生命周期，不重写全部业务算法：

1. 为 `weather.current`、`health.summary` 和 `home.light` 各建立一个最小 `CapabilityDescriptor`，只实现查询或模拟执行，验证版本协商、权限、作用域和错误码。
2. 将一个现有后台任务纳入 `TaskSupervisor`，覆盖启动、取消、热重载、超时、退避和旧实例回写拒绝。
3. 将一条现有日历记录转换为 `TemporalRecord` 和 `CalendarProjection`，保留 `daily_plan` 快照，验证时区、修订和局部重算。
4. 将一条外部健康或天气事件转换为 `Signal`，只生成候选预览，不发送消息，验证有效期、去重、严重度和审计链。
5. 让一个低风险主动类型通过 `DeliveryGateway` 走 AstrBot 标准 Agent Pipeline，验证分段、用户新消息取消、发送回执和 `uncertain` 恢复。
6. 让情绪插件以 `observe` 模式输出 `CandidateModifier` 和 `ExpressionPosture` 预览，比较新旧候选排序，不改变真实回复。

#### 3.13.5 阶段门禁和回滚

每个阶段必须同时满足功能、资源和兼容三类门禁：

- **功能门禁**：DTO 能被独立校验，状态转换有测试，失败和取消均有明确结果；
- **资源门禁**：记录模型调用、Token、内存、网络、媒体大小、任务数和页面加载耗时，不能以无限重试或无限缓存换取成功率；
- **兼容门禁**：缺少扩展、旧版 AstrBot、不同平台或 Provider 不可用时，主链仍能降级运行，并说明具体能力不可用原因。

影子运行保留输入引用、决策摘要、结果状态和策略版本，不复制原始隐私数据。出现重复投递、权限误判、作用域泄漏、任务无法收口或资源超预算时先停止受影响的新路径副作用，再按 4.1 检查数据和回执能否回退。不能只切代码开关，也不能把未修复的旧路径当作权限故障的回退方案。

### 3.14 现有插件差距与架构补齐主线

前面的章节已经定义了作用域、能力注入、日历、情绪、动机、主动调度和诊断。本节把对照十个现有插件得到的遗漏重新归并，作为重置时的架构目录和验收边界。它不再按插件增加一组互相依赖的特殊接口，而是把相同的问题收敛到横切主线。

#### 3.14.1 现有能力覆盖矩阵

“已覆盖”表示设计稿已有相应方向的契约；“待补齐”表示还没有足以约束实现的统一协议，并不代表现有插件没有这项功能。

当前重建批次按优先级分层：第一优先级是记忆、现实触及和实时共处；第二优先级是生图、创作、直播、屏幕和游戏。创作中的 QQ 空间工作台与问题治理属于暂缓外围能力，保留在盘点矩阵中，但不参与当前主链和公共契约冻结。

| 主线 | 归并的问题 | 最小统一契约 | 优先级 |
| --- | --- | --- | --- |

| 外部连接、Session 与安全 | 设备、移动网关、房间、直播和 WebSocket 各自维护凭证与生命周期 | ConnectionProfile、CredentialRef、ConsentGrant、SessionRecord、Lease、Ticket | P0/P1 |
| 模型、媒体与资源治理 | 模型成本、图片/音视频、缓存和后台任务没有统一预算 | ModelTask、ProviderCapability、MediaAssetRef、MediaJob、ResourceLease、CostRecord | P1 |
| 场景、世界、学习与人格表现 | 群聊、角色世界、学习、Bot 自我资料、创作和表达资产分散 | SceneState、PersonaWorldModel、EmbodimentState、HabitModel、LearningProposal、KnowledgeEntry、StoryProject、ExpressionAsset | P1/P2 |
| 控制面、诊断、迁移与运维 | 配置、页面、审计、回放、备份和恢复各自实现 | ConfigRevision、DiagnosticFinding、AuditEvent、ReplayRef、MigrationCheckpoint | P0/P1 |

优先级含义如下：

- P0 是相关切片启用真实副作用或迁移数据前必须冻结的最小协议。不要求一次冻结全部领域 Schema；只读适配与影子验证可先行。不满足时可能出现串号、泄露、重复投递、错误执行或数据丢失。
- P1 是需要逐步完善的运行能力，其接口、资源归属与失败语义在初期由原生插件共同设计；首期样板涉及的最小运行支持随样板交付，完整规模治理可随后补齐。
- P2 是可在领域迁移阶段逐步完善的体验能力。它们不应继续创建新的跨插件私有依赖。

#### 3.14.3 各主线的设计边界

**运行时身份与权限**

RuntimeScope 只描述本轮运行位置；SubjectRef 描述参与者；IdentityLink 描述跨平台身份关系；RelationshipEdge 描述关系事实；PermissionGrant 描述授权。五者不能互相代替。跨平台身份不能凭昵称自动合并，跨 Bot 或人格的记忆必须经过显式授权。

调用保留完整作用域，数据按 3.2.2 的稳定归属保存。隔离验证同时覆盖“禁止的共享”与“允许的连续性”：不同 Bot/人格不能串线，同一人格的日历和已授权的长期关系也不能因新线程或绑定版本变更而丢失。

**对话主链与消息投递**

Kernel 只协调陪伴体系已接入的回复和主动消息；AstrBot 保留主 Agent、工具执行、原生发送与历史写入的所有权。扩展在逻辑阶段提交贡献，阶段不等于重造宿主事件循环：

~~~text
ingest -> context -> plan -> tool -> review -> delivery -> persistence
~~~

工具执行可以多轮返回 plan；各阶段明确输入、贡献去重键、超时和失败回退。被动回复通过宿主 hook 适配贡献，由 AstrBot 发送；主动调用通过已验证的标准 Agent 入口，交给同一投递协调层。每轮显式指定 `delivery_owner=astrbot|companion` 与 `history_owner`，避免宿主和 Gateway 同时发送或写两次历史。无法截获可靠宿主回执的路径先做观察适配，不声称已具备完整投递保证。

接管开关按功能和作用域生效，扩展原有独立命令与未接入的第三方插件继续由宿主管理。实时字幕、音频帧、嘴型和游戏状态由领域 Session/Adapter 在既有授权内传输；共享回执与审计语义，不逐帧运行主动候选、LLM 或 ContactBudget。面向聊天窗口的新接触才进入主动接触预算。

**记忆、证据与知识权威**

所有进入模型上下文的内容都要带来源、作用域、有效期、可信度和敏感级别。系统必须区分用户明确陈述、外部观测、日历承诺、历史记忆、模型推测和动作回执。

模型只能提出 MemoryMutation 建议；稳定记忆的写入、强化、衰减、归档、删除和回滚由 Memory Service 根据来源和策略完成。记忆召回必须有预算和证据引用，不能用“召回更多”掩盖上下文膨胀。

**外部连接、Session 与安全**

外部插件拥有自己的连接实现、凭证和领域数据库，但凭证引用、授权状态、连接健康、重连和撤销由统一生命周期管理。房间、通话、游戏和直播都使用 SessionRecord 表示，临时记忆与持久记忆分开。

同进程插件不是安全沙箱。协议必须降低误用范围，但不能声称可以阻止恶意插件访问文件和网络。因此高风险设备动作、付费服务、精确位置、健康数据和原始媒体都必须有独立授权、审计和撤销入口。

**模型、媒体与资源治理**

模型调用先声明任务类型和资源预算，再由 ModelGateway 选择 Provider。失败时按任务执行超时、重试、备用模型和冷却，不由每个功能自行无限重试。

大文件和原始媒体不进入事件总线。MediaAssetRef 只传递所有权、用途、有效期、访问范围和存储引用，解析时重新校验 ACL；MediaJob 负责生成、取消、去重、清理和最终投递。资源预算按安装、Bot、人格、会话分层，按 3.8 的有界队列与公平调度减少互相影响，不承诺同进程的绝对性能隔离。

**场景、学习与人格表现**

群聊是独立场景域，包含观察、唤醒、插话、成员关系、公开/私聊边界和群隐私，不能当作私聊的放大版。

世界书、角色设定、用户资料、关系事实、记忆、日历和模型推测必须有权威等级。学习系统只提交 LearningProposal，经过证据、审核、启用、停用和回滚后才影响策略。Bot 自我日记、创作作品和表达资产属于人格生活资料，不能覆盖系统人格和权限。

**控制面、诊断、迁移与运维**

主插件控制面负责扩展发现、能力协商、配置层级、任务和资源状态、诊断、审计、备份和迁移；Feature Service 继续拥有自己的领域数据和算法。

诊断结果必须可以追溯到检查版本、时间、作用域和证据。修复只能先形成 RepairProposal，再经过确认和审计。迁移必须有 schema 版本、检查点、备份、恢复和按作用域删除能力。

#### 3.14.4 外部作者的最小接入面

外部插件不需要了解 Kernel 内部类，也不需要接管主对话链。根据功能类型，作者只实现以下一种或多种提供方：

| 提供方 | 用途 | 典型扩展 |
| --- | --- | --- |
| ObservationProvider | 提供健康、位置、天气、屏幕或设备状态 | 现实、屏幕、环境 |
| EventSource | 上报到家、预警、直播、游戏和 Webhook 事件 | 现实、直播、游戏 |
| ContextProvider | 提供带证据的场景或关系上下文 | 记忆、识屏、世界书 |
| CandidateProvider | 根据事件生成主动候选 | 天气、健康、内容、直播 |
| ActionProvider | 执行设备、媒体、平台或创作动作 | 米家、生图、TTS、游戏 |
| SessionProvider | 管理房间、通话、观影和实时协作 | 共处、游戏、直播 |
| AssetProvider | 提供图片、音频、视频和表情资源 | 生图、TTS、Live2D |
| DiagnosticCheck | 提供只读健康检查和证据 | 问题治理、各领域扩展 |

每个提供方都必须通过 manifest 声明版本、权限、作用域、资源预算、生命周期、失败策略和撤销行为。主插件负责注册、授权、调度和审计，扩展负责领域实现和数据所有权。

#### 3.14.5 重置门槛和实施顺序

重置不能只以“新 Kernel 能启动”为完成标准，必须按以下顺序通过门槛。各样板由 3.1.1 的原生插件提供真实接入，不能全部替换为假想市场扩展：

1. **原生联合设计与契约验证**：为九个原生插件完成最小契约记录，以 5.2 场景检验 Scope、身份、权限、对话阶段、Delivery、Evidence、Memory、Session、Media 和 Migration 的实际边界；按已验证切片冻结字段及错误码。
2. **主链样板**：让一个被动回复和一个低风险主动类型共用 ConversationPipeline 与 DeliveryGateway，验证多插件注入、合并、取消、幂等和回执。
3. **数据安全样板**：用两个 Bot、两个人格、两个会话验证身份、关系、记忆、日历、额度和任务按归属隔离，并验证同一人格跨窗口的生活连续性；执行一次包含切换后新写入的恢复演练。
4. **连接安全样板**：接入一个只读观察能力和一个需要确认的设备动作，验证凭证引用、授权撤销、超时、离线和动作回执。
5. **资源样板**：接入一个模型任务和一个媒体任务，验证预算、取消、缓存 TTL、失败冷却和清理。
6. **完整领域迁移**：在首期联动契约及适配验证的基础上，当前批次先建设记忆、现实触及、实时共处，再建设生图、创作、直播、屏幕和游戏；QQ 空间与问题治理暂不进入本批主链。此处是当前重建设计顺序，不是插件首次参与盘点的顺序。

P0 任一门槛失败时，暂停扩展迁移，保留旧路径和兼容适配器。P1/P2 可以分批实现，但不能通过增加插件私有旁路来绕过 P0 契约。

#### 3.15 立即审计入口

3.14 中的主线可以先对现有插件做审计，不需要等待 Kernel 完成。审计要先回答“当前行为从哪里进入、经过哪些边界、由谁负责收口”，再决定是否改代码。首轮审计分为三类：

1. **静态即可执行**：Hook、发送、任务、发现、作用域键、路由、存储和平台分支可以直接从生产代码、manifest 和配置中盘点；
2. **先加观测再执行**：主动候选延后、对话占用态与无关媒体打断、日历重算、情绪/动机调制、模型和媒体资源、连接稳定性以及诊断准确率需要统一字段和影子运行；
3. **等待 P0 契约**：全量替换插件 API、搬迁数据所有权、删除兼容桥、重写页面和调整 AstrBot 主事件模型必须等作用域、主链、投递、权限、证据和迁移契约冻结。

首轮的文件、行号、检查方法和交付物见 [EXISTING_PLUGIN_AUDIT.md](./EXISTING_PLUGIN_AUDIT.md)。该清单是迁移前的事实基线，不把静态命中数量直接当作缺陷数量，也不在没有回执或运行证据时宣称行为已经发生。

#### 3.16 首个可运行落点

本轮已把控制面协议做成可以被主插件实际使用的兼容切片：

- `companion/injection.py` 提供标准库依赖的 `RuntimeScope`、DTO、能力版本解析、扩展注册表和控制面自检；旧 `Scope` 仍可读取只有用户/会话字段的历史调用。
- `PrivateCompanionExtensionAPI` 为自身建立 manifest 和 generation 绑定的生命周期状态，并提供扩展注册、状态更新、注销和控制面快照；扩展元数据不会带入凭证、原始设备数据或领域数据库。
- 同一扩展同一版本重新注册时按 manifest 替换能力集合，已经移除的能力会撤销；能力提供方必须与扩展 ID 一致，避免一个插件冒充另一个插件的能力。
- 陪伴面板新增 `/extensions/status`，现有诊断结果同时返回控制面自检摘要。快照只包含版本、状态、任务数量、依赖和错误摘要，适合管理页和答疑指令读取。

这个切片还没有替换旧的发送出口、主动循环或日历存储，也未实现本文新增的稳定 owner_key、完整投递对账与迁移验收。当前实现位于 `companion/injection.py`；`companion_kernel` / `companion_sdk` 是目标命名，首期通过现有模块演进，避免为了目录名称再造注册表。下一步先接入观测；协议校验失败时新调用返回 `unavailable/degraded`，不能经旧路径绕过授权，未接入新协议的旧插件维持原有行为。

## 4. 重置顺序

本节是唯一实施依赖顺序，3.13 的 A--I 表用于能力映射。阶段 0--1 同时建设核心与原生插件的最小联动契约；每阶段交付可回退的切片。未具备外部硬件/账号时可以验证适配契约，但不能略去设备、媒体和 Session 的设计边界，也不能声称对应实机能力已验收。

### 阶段 0：原生联合设计与基线

- 冻结现有数据格式和公共命令，记录插件清单、启动任务、页面路由、存储文件和跨插件调用。
- 根据 3.1.1 为九个原生插件建立生产方/消费方、数据所有者和最小契约记录，明确硬依赖与可选依赖；同时设计配置入口、能力状态和跨插件错误追踪。
- 盘点一个 AstrBot 实例中的所有 `bot_id`、平台账号、会话、人格绑定、主体身份映射、外部连接和凭证引用；把当前隐式单例和只有 `user_id` 的状态列为迁移风险。
- 为每个插件补充启动/停止、能力状态、内存/缓存、任务数量和最近错误的诊断快照。
- 保存主动系统的策略资产目录和行为基线：候选排序、去重合并、冷却、延后、对话占用态、无关媒体打断、发送回执、专项事件和用户反馈指标。
- 建立 P0 契约草案与原生场景映射，列出消息投递、权限、证据、记忆、Session、媒体和迁移的最小字段及错误码，待阶段 1 联动验证后按切片冻结。
- 建立 UTF-8、静态检查、契约测试、资源指标和迁移回滚基线。

### 阶段 1：核心与原生联动骨架

- 基于 `companion/injection.py` 和现有桥接同时建立核心与原生插件的最小适配器，覆盖上下文、记忆、异步媒体、观察/动作、Session 和诊断的联动形态；以 5.2 场景驱动公共接口定型。
- 实现 `ScopeResolver`、`PersonaBindingStore`、`persona_binding_revision` 和唯一发送协调器；所有回调、缓存、任务、主动队列、提示词贡献和审计记录先经过作用域解析。
- 固定 `ingest -> context -> plan -> tool -> review -> delivery -> persistence` 的 Hook 顺序，让被动回复和主动消息共用一条主链。
- 建立 `PolicyRegistry` 和 `PolicyAsset` 最小实现，先加载 `legacy-compatible` 策略版本。
- 每个原生插件至少一条实际领域路径通过 DTO/API 验证，保留生产兼容入口与影子隔离；其余内部业务随领域批次迁移。分别验证全套联动、精简安装、扩展缺失、混合版本和热重载。
- 根据联动差异修订并冻结本批公共契约，记录所有受影响的生产方/消费方与兼容版本，再启用对应生产路径。

### 阶段 2：存储和日历

- 先建立 `MigrationCheckpoint`、一致备份、单一权威写入、可恢复镜像和按归属删除能力，再开始转换存量数据；不做两库独立双写。
- 先迁移日历/日程，因为它同时影响主动行为、记忆、现实提醒、创作和页面。
- 将旧 `daily_plan` 与日历记录转换为新模型，保留可回滚快照；日计划改为局部投影，兼容窗口内旧全天快照只读保留，不能驱动新路径主动行为。
- 迁移用户、主体、人格、关系、记忆和主动队列时按 3.2.2 构造稳定归属，保留原键映射与来源；绑定 revision 不进入长期实体主键。
- 依据阶段 0 已确认的数据所有权，按领域批次迁移各扩展业务表；为无法区分旧 Bot/人格的数据保留“待确认”状态，不自动合并。

### 阶段 3：事件和平台适配

- 完善阶段 1 已验证的消息、媒体、会话、设备、网络和凭证适配器，扩展到真实平台及完整业务；连接、房间、通话、游戏和直播按各自所有者纳入生命周期监督。
- 将首期已有的授权撤销、票据、取消与回执语义扩展到完整平台路径，补齐断线恢复、重放保护、动作确认和外部内容脱敏的真实环境验证。
- 逐个移除业务代码中的平台判断，先覆盖 QQ/OneBot，再补 Telegram、Discord 等平台能力。

### 阶段 4：页面工作区

- 实现阶段 0 已确定的原生联动工作区结构：核心、记忆、创作、生图、现实、屏幕、共处、游戏、直播和诊断模块共享配置层级、权限、revision 与能力状态；可分批替换页面，保留尚未迁移模块的旧入口。
- 旧路由至少保留一个发布周期，并以客户端迁移证据及使用统计决定退役；转发保留方法、鉴权、正文与状态码，不把写请求简单变成浏览器重定向。

### 阶段 5：功能迁移和退役

- 按当前优先级先迁移记忆、现实触及和实时共处，再迁移生图、创作、直播、屏幕和游戏；QQ 空间与问题治理暂缓。各模块保留首期已验证的 P0 契约及最小资源控制，随完整迁移补齐规模治理。
- 每个模块完成影子运行和行为指标对照后再退役旧规则；没有等价策略资产和回滚版本时，不删除已有专项判断。
- 每个模块验证其实际涉及的契约、资源、热重载、连接、隔离和平台场景后，按 4.1 退役旧兼容门面及重复管理页面；纯文档或局部调整不要求完整插件测试。

### 4.1 单一写入、影子运行与回退

| 阶段 | 生产所有者 | 新路径权限 | 切换依据 |
| --- | --- | --- | --- |
| observe | 旧路径 | 读取同一版本输入，在隔离投影中计算；不注入、不发送、不写生产记忆 | 差异原因可解释，资源开销在预设预算内 |
| mirror | 旧路径 | 从旧库事务 outbox 或可恢复检查点重建新库 | 存量映射与增量追平；记录 high-water mark |
| active | 新路径，按领域/作用域切换 | 先停止旧写入、等待在途操作，再以新 generation 接管 | 一份生效路由、一位写入者；外部在途动作保留对账 |
| retire | 新路径 | 旧代码只读保留至兼容窗口结束 | 行为与资源达标，恢复演练通过，已知客户端迁移完成 |

快照使用 SQLite 在线备份或暂停相关写入后的一致快照，不能只复制正在写入的 `.db` 文件而遗漏 WAL。无事务 outbox 的旧 JSON 状态先采用短暂停写快照及明确检查点，不假装具备可靠增量镜像。

回退先关闭新副作用并对账在途动作，再处理切换后的新增数据。只有旧格式能无损表示新写入、反向增量已追平且校验通过时才切回旧代码；否则保留新库、降级受影响功能并修复，不能恢复旧快照丢弃新数据。已经发送的消息、付费任务和设备效果不随数据库回滚而撤销。

影子执行复用同一输入版本、时钟和可复现随机种子，使用独立写入空间与资源预算；需要额外模型调用时抽样并计费。每批记录覆盖场景、样本数、观测时段、差异及回退版本，不能只以“运行了一个周期”判定完成。

## 5. 重置启动切片

首批交付是核心与原生联动插件共同运行的最小体系，复用现有业务算法与兼容入口。完成以下基础切片，并用 5.2 的原生场景验证；市场方案样例仅作补充：

1. 为核心及九个原生插件明确能力生产方/消费方，建立 `CapabilityDescriptor`、`Scope`、主体身份、权限、`CompanionEvent`、`EvidenceRef`、`ActionResult`、`DeliveryReceipt` 以及记忆、媒体、Session 引用的最小契约，并接入各插件现有适配入口。
2. 实现 `ConversationPipeline`、`DeliveryGateway` 和 `TaskSupervisor`，让一个被动回复和一个低风险主动类型共用主链，验证合并、取消、幂等、重载和错误诊断。
3. 建立 `MigrationCheckpoint`、备份和恢复演练，为现有日历记录建立带时区、来源和证据的只读映射；兼容窗口内旧 `daily_plan` 可继续服务旧页面/命令，但新投影只读取局部事实，不把旧全天快照作为主动触发器；正式接管事实归属在阶段 2 完成。
4. 用两个 Bot、两个会话和两个人格建立隔离与连续性矩阵；受影响绑定的旧候选失效，同一人格的长期状态仍按稳定归属恢复。

基础切片与原生联动场景共同通过后，才把对应公共契约标记为稳定；再依据第 4 节依赖和诊断数据安排完整业务、数据与页面迁移。单独完成核心启动或 manifest 注册不代表首期联动完成。

### 5.1 首批验收场景

以下是待实现的验收要求，不是本次文档修订的测试结果。每个切片只执行受影响场景；平台场景使用实际支持能力，无法提供送达回执的平台验证 accepted/uncertain 分支。

| 场景 | 必须观察到的结果 |
| --- | --- |
| 同一用户在两个 Bot/人格，及两个会话之间切换 | 禁止的资料不可见；同人格跨窗口日历保持连续，切回人格恢复长期状态 |
| 群中两名成员具有不同私聊人格绑定 | 群人格不随发言人变化；成员关系投影仍分别生效 |
| 记忆细节、否定、时间、不同属性、来源过期及无权数据增长 | 通过专项审查的精度反例回归；答案所需完整证据进入上下文，缺失/冲突明确表达；无权候选不挤占合法召回 |
| 单事件重复、乱序、修订、撤回与重启重放 | 无重复情绪累加或外部动作；投影收敛到有效版本，承诺不因 TTL 被删除 |
| 两个候选竞争最后一个接触额度 | 最多一次预算认领成功；未提交取消释放预留，未知发送保守对账 |
| 文本成功、图片失败；提交后断线 | 已成功部分不重发；回执与历史一致，不支持查询/幂等时不自动重试未知部分 |
| 人格切换、用户插话、卸载发生在生成或投递中 | 旧未提交动作失效；已提交动作保留回执，同主题机会可吸收，无关提醒保留 |
| 用户正在连续聊天并处于散步等活动，角色内部产生吃饭/拍照事件 | 对话占用态为 `engaged_thread`；无关图片候选进入 `deferred(conversation_busy)`，当前回复不被插话；话题收束后才重新评估，用户询问时可同主题合并 |
| 夏令时、跨日、全天、重复例外及确认后版本冲突 | 区间与 occurrence 稳定；旧确认不能覆盖新变更，模拟活动不冒充现实完成 |
| 启动、零点或外部信号刷新日历 | 新路径只生成当前段、下一转折和受影响窗口；不生成覆盖全天的 `today_events`/主动清单，未确认的软计划不触发媒体或消息 |
| 一个时间段结束后重新进入下一轮扮演 | `PromptSnapshot` 可以过期，但 `ActivityEpisode`、未完成事项和已验证偏好仍从 `PersonaContinuityState` 恢复；新回复不会退回空白角色，也不会照抄上一页日程 |
| 刷手机、安静学习、洗澡等活动跨越多个时间段，期间收到用户消息 | `ActivityProcess` 保留阶段、进度、可打断性和恢复方式；不生成逐分钟旁白，回复后从正确进度继续 |
| 习惯、路线、食物偏好和衣柜被多次使用或纠正 | `HabitModel` 按上下文和证据更新；衣物/路线/食物状态保持一致，未知项不被模型随意补齐 |
| 影子运行与旧路径同时在线 | 仅旧路径产生生产副作用；影子模型调用和存储开销可计量 |
| 切换后新增数据，再回退或恢复备份 | 新增数据与删除记录不丢失，旧格式无法表示时停止切回并明确报告 |
| 扩展/模型不可用、连接重载、两端同时保存设置 | 主回复可降级；无旧 generation 回写；设置冲突可见，实时流不挤入主动队列 |

行为指标以同场景旧版本为基线，记录样本数、P50/P95 耗时、每轮辅助模型调用、常驻内存、队列峰值及误归因样本。启用前写明环境和可接受阈值；普通对话新增同步情绪模型调用为 0，测试中的未授权动作、跨域泄漏、重复物理发送和旧实例回写为 0。资源阈值尚未测定的切片只可观察，不能宣称性能验收完成。

### 5.2 首期原生联动场景

以下场景使用真实原生插件适配路径，外部设备/网络/模型可在契约验证中替换；生产副作用只在隔离测试环境或已授权范围执行。每条路径检查共同 trace、主体/人格归属、单一写入与投递责任、取消传播和缺失能力回退，按场景保存结果。

| 编号 | 参与方与流程 | 首期需要验证的边界 |
| --- | --- | --- |
| N-01 记忆精度与角色连续性 | 核心就具体对象及当前/历史时间取得答案证据，结合日历/关系/情绪表达；有来源的事实交由记忆插件判断写入，随后纠正、修订或撤回 | 同一来源不重复注入，否定/时间/属性不失真，答案完整进入上下文；日志过期仍有授权证据或明确缺失；长期事实与情绪投影分属不同所有者，撤回传播到缓存和余波，曝光不当作确认；记忆不可用仍能对话 |
| N-02 创作与生图 | 核心请求创作上下文，创作按作品版本提出封面任务，生图返回资源引用，创作关联封面；记忆按策略保存创作进展 | 异步结果不能覆盖新作品版本，参考图权限不丢失，生成成功与发布成功分开；缺少生图或记忆不阻塞作品保存 |
| N-03 现实与屏幕观察 | 现实/屏幕插件提交各自来源的活动摘要，核心生成时间上下文和主动候选；已授权设备动作返回回执 | 相同活动可聚合但来源可追溯，观测过期/断流后降级；候选未选中不执行设备动作，回执不触发无限反馈 |
| N-04 实时共处 | 一起、游戏、直播分别建立自己的 Session，向核心提供共读/对局/弹幕上下文，消费人格表达与媒体偏好，结束后提出带可见性边界的记忆摘要 | 三类 Session 分别验证参与者、人格快照、重连/取消与输出回执；不把它们合成一个业务房间，不逐帧占用主动预算，多会话同时存在不串线 |
| N-05 联动诊断 | 核心记录上述任一链路的能力失效、版本冲突或部分失败，问题治理插件按授权读取诊断并关联问题记录 | 从问题定位到提供方、领域请求和回执；不复制原始私聊与凭证，不在诊断时自动修改配置或发起修复 |

首期覆盖矩阵同时记录每个原生插件的最小路径、上述场景结果、缺失/禁用/混合版本/热重载结果及未验证外部边界。所有原生插件的设计与适配验证纳入首期；个别硬件或平台未完成实测时只标记对应能力待验证，不能把该插件整体推迟到核心定型之后。

## 6. 不变原则

- 迁移前先备份，不因升级或回退丢弃用户数据；用户授权删除、撤回及保留期限清理按所有权策略执行，并保证恢复时不复活已删除内容。
- 未安装或未就绪的扩展必须是“不可用”，不能伪装成已连接，也不能启动无意义的扫描和重试。
- 兼容行为通过提示词约束、契约转换和明确降级表达实现；不要用越来越多的硬编码限制掩盖模型或边界问题。
- 所有源码、配置、文档和迁移文件使用 UTF-8。
- 原生陪伴联动从构建初期共同设计、接入和验证；按需安装与分批业务迁移不改变其首期设计地位。
