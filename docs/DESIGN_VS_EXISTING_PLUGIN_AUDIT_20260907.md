# 设计稿与现有插件全面对照审查

> 导航：[设计总纲](./FRAMEWORK_DESIGN.md) / [主题目录](./FRAMEWORK_DESIGN_INDEX.md)。定位：日期化差距审查；用于功能对等与风险定位，不证明新契约已实现。

> 审查日期：2026-09-07  
> 范围：陪伴核心、记忆、现实触及、实时共处，以及第二优先级插件。  
> 结论性质：设计差距审查，不代表所有现有路径都已完成运行验收。

## 1. 总体结论

现有插件并不是“只有旧功能的单体实现”。它们已经包含大量应保留的成熟能力：页面管理、命令入口、导入导出、权限校验、后台任务、重试、断线恢复、媒体适配、审计和测试。新框架当前的公共契约覆盖了这些能力的方向，但还没有把每一项都绑定到具体入口、owner 和验收案例。

因此当前风险不是“设计完全缺功能”，而是：

1. 新框架可能只迁移主对话和几个 DTO，遗漏页面、命令、后台维护和恢复路径；
2. 现有代码已经实现的作用域、缓存和兼容逻辑，与新设计中的统一语义还没有一一映射；
3. 现有插件仍有平台分支、自然语言规则和对象旁路，不能直接视为新框架实现；
4. 设计稿描述了目标状态，但部分能力还没有明确“当前是否可用、缺失时如何降级、由谁最终确认”。

## 3. 设计稿已覆盖但现有实现不足的部分

### 3.1 统一状态和事件

设计稿已经区分 `SceneState`、`AffectState`、`ContinuityState`、`MemoryState` 和 `ObservationState`。现有核心则把日状态、情绪、关系、计划、记忆投影和主动队列分散在多个 mixin、JSON/SQLite 表和后台任务中。迁移时必须先定义投影关系，不能把现有字段直接拼成一个新的“大状态对象”。

### 3.2 AI 解释与运行时约束

现有代码已经有部分结构化 DTO 和 proposal 模式，但仍能看到消息标记、正则、词表、时间表达式和平台分支参与语义路由。设计要求把这些降为 AI 输出的解释或兼容 fallback；只有权限、作用域、证据、预算、协议和生命周期继续硬校验。

### 3.3 证据级召回

现有记忆检索已经有 FTS、LIKE、向量、重排、ACL、slot 和缓存，但“命中一条记录”不保证“回答所需细节已进入上下文”。新设计需要把 Candidate、AnswerEvidence 和最终注入片段分开评估，并处理无权候选挤占、字段截断和摘要错误极性。

### 3.4 主动闭环

现有主动能力有候选、队列、冷却、预算、占用态和投递路径，但来源、动机、内容和反馈仍分散。新设计要求 `signal → motive → candidate → policy → delivery → feedback` 可追踪，未知投递不能直接算完成，无反馈不能推断用户态度。

### 3.5 连接和会话生命周期

现实和共处插件都有连接、房间、任务和重连实现，但缺少跨插件统一的 generation、ticket、lease、取消和 owner 语义。设计中的 `SessionRecord`、`TaskEnvelope` 和 `ConnectionProfile` 必须先做适配器，而不是直接替换各插件内部状态。

## 4. 现有插件已有、设计稿需要明确保留的能力

这些能力不能因为不属于“主链”而在新框架中消失：

- 命令入口、工具入口、页面入口和权限管理；
- 记忆查看、编辑、置顶、删除、纠正、导入导出和照片/日记快照；
- 记忆摘要、pending 队列、嵌入索引、访问统计、衰减、重试和死信；
- 多 Bot、多人格、私聊/群聊作用域和跨平台身份隔离；
- 主动候选的查看、延后、取消、预算、冷却和投递状态；
- 设备绑定、移动端配对、米家设备发现、摄像头/音频入口和闹钟；
- 共处房间、通话、共读、观影、媒体播放、字幕、断线重连和房间管理台；
- 生图参考图目录、任务状态、资源归属、provider 降级和发送回执；
- 创作项目、章节版本、续写、审校、封面和创作记忆；
- 直播平台连接、字幕、TTS、VTS/OBS 和重连；
- 屏幕采集、管理员私聊授权、脱敏、历史活动和远程接收；
- 游戏房间、玩家席位、受信浏览器、引擎进程、撤销绑定和结果结算；
- 页面 API 的分页、快照、媒体读取、配置 revision、诊断和备份恢复；
- 测试替身、录制数据、迁移脚本、兼容入口和热重载保护。

这些能力要进入 `CapabilityCoverage`，并标明是 `retained` 还是 `redesigned`，不能只写在插件 README 或 changelog 中。

## 5. 现有实现中需要避免带入新框架的部分

1. 用自然语言词表直接决定回复吞掉、改写、记忆写入或主动阻断；
2. 用一个 `MemoryRecord` 同时表示事件、摘要、画像、关系和外部资料；
3. 通过 `sys.modules`、模块级单例、私有属性或 `get_registered_star` 发现并调用插件；
4. 将 event/request 对象直接交给长期后台任务，导致重载和取消边界不清；
5. 多条注入路径分别实现权限、slot、缓存和去重；
6. 以固定轮数、固定词类或固定主动类型代替语义判断；
7. 把未知投递当作失败或成功，或在未知状态下无条件重试；
8. 以页面存在、工具返回或数据库写入代替真实动作回执；
9. 跨插件复制可变状态或直接读取对方 `data_dir`；
10. 把失败后的兼容回退当作权限或证据校验的替代方案。

## 6. 必须补写的设计内容

### P0：第一批设计冻结前

- 为记忆、现实触及、实时共处各完成 `CapabilityCoverage`；
- 定义三个领域的 owner、状态投影和事件来源；
- 把页面/命令/工具/后台任务列入能力清单；
- 冻结 Scope、Evidence、Consent、Session、Task、Action 和 Delivery 的错误语义；
- 明确缺失插件、权限撤销、过期、未知、取消、重载和恢复案例；
- 为记忆召回增加答案证据级验收，为主动增加反馈级验收。

### P1：纵向切片实现前

- 建立三领域适配器，不直接共享私有对象；
- 统一 generation、lease、idempotency 和 cache revision；
- 为现实观察和共处媒体定义原始数据保留、脱敏和短期会话边界；
- 为管理页面定义能力状态、降级原因、审计和恢复入口；
- 建立由旧硬编码审计表生成的多意图、否定、引用、反话和无关键词回放集。

### P2：第二优先级接入前

- 逐项补齐 Image/Content/Live/Screen/Game 的任务、资源、Session 和回执契约；
- 把媒体生成、发送、发布、外设动作和平台连接分成可独立失败的步骤；
- 记录 QQ 空间和 Bug Companion 的暂缓状态，不能让其形成新的主链旁路。

## 7. 审查结论与下一步

设计稿可以继续作为目标架构，但在进入大规模重写前还缺一份“现有入口到新契约”的逐项映射。下一步应先完成三张表：

1. **记忆能力映射表**：旧入口、数据对象、召回/写入路径、目标状态和精度反例；
2. **现实触及能力映射表**：设备/移动/摄像头/音频/闹钟入口、授权、TTL、动作回执和离线行为；
3. **实时共处能力映射表**：房间/通话/观影/共读/媒体/重连入口、参与者权限、临时上下文和结束摘要。

完成三表后再冻结第一批公共契约；在此之前只做适配和影子观测，不关闭现有功能入口。
