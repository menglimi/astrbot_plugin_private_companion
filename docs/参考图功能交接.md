# 参考图功能交接

> 适用版本：`6.0.5a`（代码核对日期：2026-08-05）
> 目标读者：后续维护参考图库、自拍/改图、图片后端和陪伴面板的开发者。

## 1. 一句话架构

参考图功能不是“把一个图片路径附加到生图请求”这么简单，而是一条完整的决策链：

```text
本轮显式改图原图或引用图片 -> 直接作为显式参考来源
参考图库 / 今日穿搭图 / 基础人设图 -> 归一化为带职责与服装元数据的候选
    -> 结合本轮请求、场景预设、日程地点和否定表达选择一张普通候选
    -> 单独完成服装裁决并清理冲突上下文
    -> 分区组装最终 Prompt 和一致性修复
    -> 向支持参考图的后端实际提交一张图片
    -> 记录选图、实际使用状态、服装裁决和完整调试 Prompt
```

必须始终区分三个概念：

- **已配置**：图片存在于基础人设图或参考图库配置中。
- **已选中**：本轮决策选择了这张图，最近生图记录中的 `reference=true`。
- **已实际使用**：图片文件存在、后端真实接收了参考图且成功返回有效成图，记录中的 `reference_used=true`。

“已选中”不等于“后端已使用”。排障和用户可见回执必须依据 `reference_used`，不能只根据路径或普通成功文案猜测。

## 2. 入口与配置

### 2.1 陪伴面板

入口为：

```text
功能开关 -> 生图/拍照能力 -> 参考图库管理
```

这是“生图/拍照能力”的三级页。页面同时管理：

- 基础人设参考图；
- 最多 24 张场景参考图；
- 每张场景图的路径、用途注释、职责、服装类别、服装锁、适用场景和首选预设；
- 预览、状态刷新、筛选、排序、添加和删除。

图片 API 的端点、模型和鉴权不在这里配置，仍在“模型 -> 生图模型”中管理。

### 2.2 关键配置项

| 配置项 | 作用 | 关键边界 |
| --- | --- | --- |
| `enable_photo_text_action` | 生图/拍照总开关 | 关闭后自拍、改图和工具生图都不可用 |
| `enable_photo_reference_image` | 自动参考图一致性开关，默认关闭 | 只控制自动读取固定人设图、图库和今日穿搭；用户本轮显式提供或引用的图片不受此开关影响 |
| `photo_persona_reference_image_path` | 基础人物身份锚点 | 本地路径或 HTTP(S) URL；运行时职责固定为 `identity`，不锁服装 |
| `photo_reference_library` | 场景参考图库 | 结构化列表，最多 24 项；旧文本格式继续兼容 |
| `enable_daily_outfit_photo` | 生成每日穿搭图 | 当天文件有效时会作为运行时 `daily_outfit` 候选参与选图 |
| `photo_generation_backend` | `auto/comfyui/sdgen/external/tool_call` | 有参考图时只会走真正支持图片输入的路径 |
| `COMFYUI_SELFIE_WORKFLOW_NAME` | 自拍、人物和改图的 ComfyUI 路由 | 参考图场景要求工作流支持 `images=1` |
| `custom_photo_tool_reference_param` | 自定义生图工具的参考图参数名 | 需要参考图却未配置该参数时，调用会终止 |
| `PHOTO_PROMPT_PROVIDER_ID` | 生图提示和参考图语义选图优先模型 | 未配置时按快速模型、主模型等现有分流回退 |
| `photo_generation_scene_presets` | 自定义或覆盖场景预设 | 同名覆盖内置预设；首选预设必须实际存在才能注入 |
| `photo_generation_prompt_format` | `traditional/natural_language` | 只改变 Prompt 表达，不改变参考图选择和后端协议 |

运行时读取集中在 `main.py`，参考图相关主配置字段为：

```python
self.photo_persona_reference_image_path
self.photo_reference_library
self.enable_photo_reference_image
```

## 4. 配置数据结构

### 4.1 推荐结构化格式

新代码和面板都应优先保存对象，不要再生成多行文本：

```json
{
  "id": "sleepwear_main",
  "path": "C:\\references\\sleepwear.png",
  "note": "米白色睡衣；在家、卧室、睡前或刚起床时使用",
  "reference_roles": ["identity", "outfit"],
  "outfit_category": "sleepwear",
  "outfit_lock_default": true,
  "scene_categories": ["home", "bedroom"],
  "preferred_preset": "居家睡衣"
}
```

读取时 `source`、`path`、`url` 都可作为图片来源字段；面板保存时统一写为 `path`。运行时还会补充 `kind`、`metadata_source` 和解析后的本地 `path`。

`id` 是运行时候选 ID。未配置时按当前位置生成 `library_1`、`library_2`。页面预览接口另有一个由 `kind + source` 哈希得到的短 ID，两者不要混用。

### 4.2 `reference_roles`

| 标准值 | 含义 |
| --- | --- |
| `identity` | 人脸、发型、人物身份和稳定外貌 |
| `outfit` | 完整服装、层次、轮廓、材质、配饰和主色 |
| `pose` | 姿势参考 |
| `scene` | 背景、地点和场景参考 |
| `style` | 画风参考 |
| `continuity` | 延续上一张图的整体视觉状态 |
| `source` | 本轮改图原图；只用于运行时，不应配置到普通图库 |

运行时接受中英文别名，例如 `persona/face/人设/脸 -> identity`、`wardrobe/clothing/穿搭 -> outfit`。未知职责会被忽略。

职责为空时会自动推断：

- 基础人设图：`identity`；
- 今日穿搭图：`identity + outfit`；
- 最近已发送成图：`identity + outfit + scene + continuity`；
- 注释明确“仅身份/只参考脸和发型”：`identity`；
- 注释或字段可推断出服装类别：`identity + outfit`；
- 其他普通图库项：`identity`。

### 4.3 `outfit_category`

当前内置裁决使用以下标准值：

| 标准值 | 默认预设 |
| --- | --- |
| `sleepwear` | 居家睡衣 |
| `homewear` | 居家服 |
| `cosplay` | COS自拍 |
| `school_uniform` | 校服人像 |
| `formalwear` | 礼服人像 |
| `swimwear` | 泳装人像 |
| `sportswear` | 运动服人像 |
| `daily_outfit` | 日常穿搭 |

`custom_outfit` 是本轮自然语言服装请求的运行时类别，不建议写入图库。管理页目前允许自由输入，因此不要填 `formal` 等看似相近但未被内置映射识别的值，应使用上表的精确标准值。

### 4.4 `outfit_lock_default`

这是三态字段：

- 字段缺失：自动推断；
- `true`：默认把参考图服装视为权威服装；
- `false`：明确不锁服装。

只有同时包含 `outfit` 职责时，`true` 才会真正形成服装锁。自动推断通常会对“有 `outfit` 职责且有服装类别”的图启用锁定。

不要把显式 `false` 当成空值清除。页面和服务端已有回归测试保证它可以往返保存。

### 4.5 `scene_categories` 与 `note`

可用的场景标签包括：

```text
home, bedroom, school, office, outdoor, formal_event, sport, beach
```

当前规则评分对 `home/bedroom/school/outdoor` 有直接结构化加分；其他标签主要依赖用途注释和语义模型理解。用途注释仍是选图的重要输入，应同时写清：

- 画面里的服装；
- 适用地点；
- 适用时间或行为；
- 明确不适用的场景（必要时）。

推荐：

```text
米白色睡衣；在家、卧室、睡前或刚起床时使用；外出和上学时不用
```

不推荐：

```text
好看的图
```

### 4.6 `preferred_preset`

首选预设只负责把预设 Prompt 纳入最终画面。它必须是内置预设或 `photo_generation_scene_presets` 中实际存在的名称。

内置服装预设和 `outfit_category` 有明确映射。自定义预设若也要参与结构化服装裁决，预设名必须能命中已知服装类别，或同步扩展 `_photo_generation_scene_preset_wardrobe_category`；只有一段自定义预设文字并不会自动产生新的服装类别。

### 4.7 旧格式兼容

以下旧格式仍可读取：

```text
C:\references\home.png || 居家服，在家或睡前使用
```

```text
C:\references\home.png || 居家服 || {"outfit_category":"homewear","outfit_lock_default":true}
```

也支持 JSON 字符串或对象列表。新增功能应保持兼容读取，但持久化应尽量转为结构化对象，以避免注释换行、显式 `false` 和未来元数据丢失。

## 5. 文件与状态存储

`self.data_dir` 来自 `StarTools.get_data_dir("astrbot_plugin_private_companion")`，通常位于 AstrBot 的 `data/plugin_data/astrbot_plugin_private_companion`，不是插件源码目录。

| 路径/状态 | 内容 |
| --- | --- |
| `<data_dir>/photo_reference_images/` | 消息附件、引用图片和远程参考图的稳定本地副本 |
| `<data_dir>/photo_prompt_debug/` | 脱敏后的完整 Prompt 调试 JSON，最多保留最近 40 个 |
| 插件配置 | 基础人设路径和参考图库结构化配置 |
| `recent_photo_generations` | 最近 48 次生图的结构化摘要 |
| `recent_photo_continuity` | 按会话和发送者隔离的最近已发送成图连续性状态 |
| `daily_outfit_photo` | 当日穿搭图的日期和文件路径等运行时状态 |

支持的本地参考图扩展名为：

```text
.png, .jpg, .jpeg, .webp
```

MiniMax 的 `subject_reference` 协议边界更窄：只提交单张 JPG/JPEG/PNG，且文件必须小于 10 MB；WebP 候选仍可供其他后端使用，但不会直接提交给 MiniMax。

通过消息添加时会复制到 `photo_reference_images`。远程 URL 在首次实际候选解析时下载为本地文件，并尝试回写配置。删除配置目前不会自动删除已经缓存的文件。

## 6. 运行时调用流程

### 6.1 工作流类型先行

统一工作流类型为：

- `text2img`：不包含 Bot 本人的普通场景、物件和风景文生图；
- `selfie`：Bot 本人以正面、侧脸、背影或环境人像等任何形式出镜的画面，以及自拍、头像、穿搭和角色表情包；
- `edit`：改图、修图、重绘和 P 图。

参考图库的自动选择只接受 `selfie/portrait` 语义。需要人物一致性的创作封面、主动配图或 QQ 空间配图，会由调用方显式按人物链路取出一张参考图，再传给生成器。

纯风景或物件图不应为了让 `reference=true` 而强行携带人设图。此类请求应从 Bot 的镜头视角描述，并通过正负提示避免后端擅自添加拍摄者、陌生人物或人物背影。如果最终画面需要出现 Bot，即使只出现背影，也必须改走 `selfie`，让人设参考图链路参与身份一致性。

### 6.2 显式改图是独立分支

`陪伴 改图` 和 `pc_generate_photo(kind="edit")` 必须有本轮发送、引用或显式传入的图片。图片会先稳定落盘，再以如下元数据进入生成器：

```json
{
  "id": "explicit_reference",
  "kind": "source",
  "reference_roles": ["source"],
  "outfit_lock_default": false
}
```

改图链路不会：

- 自动替换为基础人设图；
- 注入自拍构图；
- 注入当前日程、地点或今日穿搭；
- 套用自拍场景预设；
- 把原图恰好与图库同路径当成图库服装参考。

最终 Prompt 会加入 `Image edit contract`，要求原图是唯一画布，只修改用户明确要求的部分。ComfyUI 底层可以复用自拍/图生图工作流，但上层 `workflow_kind` 仍必须保持 `edit`。

普通自拍的显式来源规则在三个用户入口保持一致：`pc_generate_photo(kind="selfie")`、`rule_fast` 自然语言自拍和“陪伴 自拍/拍照”命令都会优先解析本轮携带或引用的图片。解析到图片时，它直接作为显式参考来源进入后续职责、服装、场景和 Prompt 连续性处理；本轮没有图片时，才进入基础人设图、参考图库和今日穿搭的普通选图流程。

### 6.3 自动候选集合

开启 `enable_photo_reference_image` 后，自拍/人像候选按以下来源构造：

1. 参考图库中本地可用或成功缓存的图片；
2. 当天有效的今日穿搭图（调用方允许时）；
3. 基础人设图（路径未与前面重复时）；

最近成图不再由选图器自动插入候选，也不会因为“继续拍、再来一张”等文字被直接强选。只有用户本轮显式引用或携带图片时，该图片才作为显式参考来源进入后续职责、服装和 Prompt 连续性处理。最近成图仍只在生成成功且实际投递成功后登记，连续性键继续按会话和发送者隔离，供选图器之外的连续性判断与排障使用。

### 6.4 选图

选图上下文包含：

- 当前日程和地点；
- 本轮用户的正向画面要求；
- 结构化 `requested_scene_preset`；
- 明确的服装否定项。

规则评分重点包括：

- 服装类别精确匹配；
- 用途注释与当前居家、睡前、外出、运动、正式或 COS 场景匹配；
- `scene_categories` 匹配；
- 居家/睡前场景对今日外出穿搭的强降权；
- 用户明确排除某服装时的强降权；
- 自定义换装时对旧锁服装参考的降权。

存在多个普通候选或专用职责图时，会调用语义模型选择候选编号。模型可以输出 `0` 表示全部不使用。模型不可用、报错或输出无效时使用可审计的规则兜底。本轮显式提供或引用的图片不参与这一步普通候选竞争。

结构化场景预设是更高优先级约束。如果指定“居家睡衣”，并且有 `sleepwear` 候选，选图器会优先保证同类参考图，而不会接受模型返回的冲突服装图。

### 6.5 服装裁决

选图之后还必须单独执行 `PhotoWardrobeDecision`。主要优先级为：

1. 结构化 `requested_scene_preset` 对应的服装类别；
2. 本轮用户明确要求的新服装；
3. 本轮用户明确排除的服装；
4. 今日穿搭参考图；
5. 本轮显式引用的最近已发送成图所提供的自然续拍约束；
6. 带 `outfit` 职责且默认锁服装的图库参考图；
7. 日程中的今日穿搭上下文；
8. 仅人物身份参考；
9. 无服装来源。

常见 `wardrobe_mode`：

```text
explicit_preset, explicit_prompt, explicit_exclusion,
daily_outfit, continuity, reference_outfit,
daily_outfit_context, identity_only, source_edit, none
```

如果本轮要求与已选图服装冲突，通常不会丢弃整张参考图，而是从 `effective_reference_roles` 中移除 `outfit`，继续只参考身份或其他兼容职责。这是有意的柔性约束，避免用过硬逻辑阻断合理换装。

### 6.6 一致性清理与 Prompt 组装

服装裁决完成后，生成器会：

1. 检查结构化预设、服装类别、锁定状态和今日穿搭删除状态是否一致；
2. 物理删除冲突的今日穿搭场景文字和旧的“保持今日穿搭”连续性文案；
3. 确定最终场景预设；
4. 按分区预算组装 Prompt；
5. 检测残留服装/预设冲突，并追加柔性冲突解决提示；
6. 写入完整调试 JSON；
7. 再提交后端。

最终 Prompt 分区为：

```text
user_request
reference_wardrobe
scene_style_preset
composition_continuity
negative
```

传统格式使用 `Positive prompt/Negative prompt`，自然语言格式在末尾使用 `Avoid ...`。场景预设不会再简单拼到完整 Prompt 尾部，因此不会误落入 Negative prompt。

## 7. 后端契约

当前生成器只向后端提交**一张**参考图。图库的 24 张是候选集合，不是一次性多图输入。

| 后端/平台 | 参考图方式 | 当前行为 |
| --- | --- | --- |
| OpenAI 兼容 | `/images/edits` multipart | 依赖具体服务真正兼容 edits 接口 |
| Agnes | generations JSON，参考图 Data URI 放入 `extra_body.image` | 支持 |
| MiniMax | `/v1/image_generation` JSON，人物参考图放入 `subject_reference` | `image-01` / `image-01-live` 均支持；当前只提交一张 PNG/JPEG 人物图 |
| 百炼 | 多模态图片生成路径 | 支持；有参考图时失败不会再退回异步纯文生图 |
| Gemini | 多模态内容中的图片数据 | 支持 |
| ComfyUI | `images=1` 输入工作流 | 支持；工作流不接收图片时终止 |
| 自定义函数工具 | `custom_photo_tool_reference_param` 指定的路径参数 | 目标工具和参数都必须支持 |
| SDGen | 无参考图输入 | 不支持，有参考图时跳过/失败 |
| 魔搭 ModelScope | 当前文生图接口 | 不支持 |
| 豆包/火山方舟 | 当前文生图接口 | 不支持 |
| SenseNova U1 Fast | 官方纯文接口 | 不支持 |

可靠性原则是 **fail closed**：参考图已经被选中后，读取失败、提交失败或后端不支持时，不允许静默改成纯文生图。`auto` 可以从在线 API 回退到仍携带同一参考图的 ComfyUI，但不会再回退到不支持参考图的 SDGen。

`_conf_schema.json` 与运行时保持一致：已经选中参考图时，找不到可接收图片的 ComfyUI 工作流会明确停止，不会静默回退为纯文生图。

## 8. 管理页面实现

服务端接口：

```text
GET /photo_reference/list
GET /photo_reference/image_data?id=<allowlisted-id>
POST /photo_reference/metadata/compile
POST /photo_reference/metadata/review
POST /photo_reference/selection_trial
```

关键安全边界：

- 本地预览只接受当前配置中已登记图片对应的哈希 ID，不能用任意路径读取主机文件；
- 本地预览单文件上限为 20 MiB；
- 远程图片使用原始 URL 直接预览；
- 页面新增“路径或 URL”只编辑配置，不负责把浏览器本机文件上传到 Bot 主机；
- 删除需要二次点击确认；
- 三级页复用功能详情草稿、统一保存和未保存提醒。

参考图库卡片不再要求维护者直接理解 `reference_roles`、`scene_categories` 等内部字段。点击“添加参考图”或卡片上的“配置使用方式”后，页面通过最多 8 道选择题收集用途证据；多道题可以共同指向同一元数据职责，再由 WebUI 模型配置中的主模型审批合并。审批不可用时会保留明确警告并使用确定性本地合并，专家 JSON 覆盖必须单独开启并标记为 `manual_override`。

目录当前版本为 v2。`editor_intent` 保存可恢复的维护者答案，其余规范字段供正式选图器消费；旧 v1 条目只恢复能够无损推导的答案，无法确认的穿搭、地点和姿势行为必须由维护者重新选择后才能保存。

“选图试跑”先通过 AstrBot 原生 Function Calling 让主模型决定是否调用 `pc_generate_photo`，只捕获 `kind`、`prompt`、`scene_preset` 等参数，不执行工具。随后使用页面中的未保存草稿目录运行正式选图器，并报告规范化请求、候选匹配/排除/分数/排名、模型选择、规则兜底、预期参考图是否命中和三次稳定性。当前上下文模式只读加载用户摘要、人格正文、日状态、日程和最近会话；空白或自定义上下文不会创建或修改会话。

试跑禁止生成、下载或发送图片，不消耗生图额度，不写入聊天历史、正式 trace、最近成图、连续性或使用记录，也不修改用户、日程、状态和正式配置。

图库顺序会影响模型候选编号，以及规则评分相同时的兜底顺序，但不是无条件优先级。真正优先级仍由显式请求、场景、元数据和评分决定。

## 11. 排障流程

### 11.1 页面检查

1. 打开“排障 -> 图片链路”。
2. 使用“测试自拍”验证真实参考图链路。
3. 不要用模型页的“纯文测试”判断参考图是否可用；它故意不上传参考图，也不测试自拍、改图和角色一致性。
4. 打开“最近生图记录”，核对本轮 trace、选图、服装裁决、最终预设和调试文件。

### 11.2 日志关键字

```text
参考图库候选评分
参考图库已选图
指定场景预设一致性已自动修正
生图提示词冲突已柔性修复
生图开始
生图结束
```

`参考图库已选图` 日志会给出：

```text
source, reason, id, kind, fallback, model_reply, path, note, candidates
```

其中 `source` 常见值为：

```text
model, rule_fallback, single_candidate, semantic_preset, semantic_exclusion
```

### 11.3 最近生图记录

优先检查：

| 字段 | 解释 |
| --- | --- |
| `reference` | 本轮是否选择了参考图路径 |
| `reference_used` | 后端是否实际接收参考图并成功成图 |
| `reference_id/kind/roles` | 选中了谁、来源是什么、原始职责是什么 |
| `reference_outfit_category` | 候选图声明的服装类别 |
| `wardrobe_mode/source/category` | 最终服装裁决，而不是原图元数据 |
| `outfit_locked` | 最终是否锁定一套服装 |
| `daily_outfit_removed` | 是否要求移除今日穿搭上下文 |
| `presets` | 最终真正应用的预设 |
| `conflicts` | 最终 Prompt 检出的冲突 |
| `removed_conflicts` | 已物理清理或一致性修复的冲突来源 |
| `prompt_hash/path` | 最终 Prompt 哈希及完整调试文件 |

### 11.4 Prompt 调试 JSON

调试文件位于 `<data_dir>/photo_prompt_debug`，内容会经过凭据脱敏。重点字段：

```text
requested_scene_preset
base_prompt
scene_context_before
scene_context_after
reference
wardrobe_decision
presets
prompt_sections
conflicts
removed_conflicts
final_prompt
final_prompt_length
final_prompt_sha256
```

快速判断：

- `reference=false`：没有候选、开关关闭、工作流不是人物链路，或模型明确选择 0；
- `reference=true, reference_used=false`：图片已选但后端未成功实际使用，继续看 `note` 和后端日志；
- `requested_scene_preset=居家睡衣` 但 `wardrobe_category!=sleepwear`：结构化一致性链失效，应视为代码回归；
- `daily_outfit_removed=true` 但 `scene_context_after` 仍含具体今日穿搭：清理链回归；
- `kind=edit` 却出现自拍构图、日程或今日穿搭：改图语义回归；
- 图片生成成功但 `reference_used=false`：不要向上层宣称参考一致性成功。

## 12. 已知边界和技术债

1. **一次只提交一张参考图。** 多图仅用于候选管理，不是多参考图融合。
2. **模型能力仍是上限。** `reference_used=true` 只能证明图片已提交，不能保证像素级身份、服装或场景还原。
3. **页面按路径去重，不按内容去重。** 同一文件复制到不同路径后仍可形成多个配置项；内容指纹去重目前只覆盖单次消息收集。
4. **命令修改会降级结构化元数据。** 见第 9 节，应优先用面板维护高级元数据。
5. **远程缓存回写可能丢失扩展字段。** `_photo_reference_config_value` 当前重建的是已知字段；远程 URL 缓存成路径时，显式 `id` 和未知未来字段不保证保留。修复时应从原对象复制后仅替换来源字段。
6. **场景标签不是完整分类器。** 结构化直接加分主要覆盖 `home/bedroom/school/outdoor`，因此 `note` 仍必须写完整语义。
7. **页面高级字段输入较宽松。** 服务端会忽略未知职责，未知服装类别也不会自动映射到内置预设。
8. **自定义预设名不自动创造服装类别。** 需要结构化服装裁决时必须补类别映射和冲突检测。
9. **缓存文件不会随配置删除。** 清空图库只移除配置，不清理 `photo_reference_images` 中的历史副本。
10. **最近成图连续性只来自实际发送成功的图片。** 生成但未发送的图不会登记；已登记图片也不会自动进入选图器，只有本轮显式引用或携带时才参与后续连续性处理。
11. **基础人设图元数据固定。** 当前三级页只能编辑其路径，职责固定为 `identity` 且不锁服装；需要服装职责时应放入场景图库。
12. **Schema 中仍有旧提示。** ComfyUI 参考图失败的实际策略是停止纯文回退，后续应同步配置提示文案。

### 13.1 新增服装类别

```text

_photo_generation_scene_preset_wardrobe_category
```

同时补充：自然语言正向/否定、结构化场景预设、冲突参考图降级为身份职责、今日穿搭清理和调试字段测试。

### 13.2 新增参考职责

至少同步检查：

```text
_photo_reference_normalize_roles
_normalize_photo_reference_candidate_metadata
_photo_generation_reference_wardrobe_section
选图模型候选说明
管理页编辑器
```

职责必须真正影响最终 Prompt 或后端协议，不能只增加一个无法消费的元数据标签。

### 13.3 新增参考图后端

必须满足：

1. 图片在提交前转换成功；
2. 后端请求中可证明参考图真实存在；
3. 失败时不静默转纯文；
4. 成功后把 `reference_submitted=true` 传给统一结束记录；
5. 返回文件必须真实存在；
6. 补充成功、读取失败、接口失败和路径包含空格/长路径的测试。

### 13.4 修改配置持久化

必须保留：

- 显式 `outfit_lock_default: false`；
- 自定义 `id`；
- 未识别的未来扩展字段；
- Windows 长路径和连续空格；
- 多行注释（配置层）；
- 原有顺序。

## 15. 最后检查清单

- [ ] 显式改图原图仍是 `source`，没有被改写成自拍或人设参考图。
- [ ] `scene_preset` 仍以结构化字段传递，没有拼进 Prompt 尾部。
- [ ] 用户明确换装或否定服装时，冲突参考图只保留兼容职责。

- [ ] 有参考图时不会落到 SDGen 或其他纯文路径。
